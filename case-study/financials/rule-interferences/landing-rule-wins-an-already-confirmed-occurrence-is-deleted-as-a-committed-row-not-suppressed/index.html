Landing rule wins — an already-confirmed occurrence is deleted as a committed row, not suppressed

Title

Landing rule wins — an already-confirmed occurrence is deleted as a committed row, not suppressed

Condition

A delete request names an r-prefixed instance id whose occurrence date has already landed and been confirmed into the ledger, and the resolver reaches the instance test last.

Summary

Where confirmation and suppression compete for the same date, landing wins: the committed-row path claims the id before the suppression path sees it, so the deletion becomes a real journaled removal of what landed.

Description

Two rules of this process can claim the same projected date. The suppression rule says: an instance id belongs to the rule's projection, and removing it excepts the date. The confirmation rule says: once an occurrence has landed and been confirmed, it is committed money, and committed money only leaves through the journaled deletion discipline. The code makes the precedence concrete in the resolver's order — the ledger is searched first, so a landed-and-confirmed occurrence resolves as a committed row and goes to the real-mutation path with its full audit; the instance test runs last and only ever sees dates still projected. The recurrence side's own docstring records the intent: the instance window is built so landed-but-unconfirmed cases stay resolvable — the genuinely contestable band — while fully confirmed money is no longer in the instance game at all.

  """Resolve an r:-hash id to (rule, occurrence) among the ACTIVE rules'
  projected instances in [anchor − grace, +400d] — the same window as the
