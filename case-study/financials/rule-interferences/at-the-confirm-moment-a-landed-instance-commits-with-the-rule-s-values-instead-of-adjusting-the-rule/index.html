At the confirm moment a landed instance commits with the rule's values instead of adjusting the rule

Title

At the confirm moment a landed instance commits with the rule's values instead of adjusting the rule

Condition

When the occurrence of a standing commitment has landed and the owner names that instance for confirmation, the confirm moment and the rule values meet the edit moment and its adjustable fields.

Summary

At confirmation the rule carries the day and the confirm moment wins — the landed occurrence commits straight from the rule's values, never re-asks or re-shapes the rule, and the interactive future-instance path only allows the date to shift down to today.

Description

Two claims meet at a landed rule occurrence. The confirm moment claims the instance commits as it stands — the values come from the rule, zero-prompt, and the projected occurrence leaves the open backlog as soon as the real row covers the period. The edit moment claims each field is adjustable — amount, category, cadence, dates.

Confirmation wins at the confirm moment. The interactive path that handles a future-scheduled instance exists precisely for the bill that arrived early: it asks questions, but description, category and amount are prefilled from the rule and every Enter keeps the rule's value — the only freedom granted is the date, and only downward to today. The refusal message for pushing the date past today says where the adjustment belongs — the edit flow, which changes all following occurrences — not at the confirm moment.

The books' branching makes the precedence explicit — the confirm path commits directly without asking, or asks only with the rule's values prefilled; the edit path is a separate act on the rule.

Visible Effect

A bill that landed as scheduled is booked with the rule's own values and no questions; a drifted bill is still booked as it landed, and correcting the rule for the future remains a separate, later act.

def _confirm_instance(entry_id: str) -> int:
  """Confirm a rule instance (r:-hash). LANDED instances commit
  zero-prompt with the rule's own values (a covering commit supersedes
  the instance automatically, nothing to record). A FUTURE instance
  opens the prefilled prompts (the same walk as edit's landed branch:
  datum first, shiftable down to today) so an early-landed bill can be
  confirmed interactively; recurrence_cli's own future-date gate
  refuses an actual dated ahead of today."""
  from financials import recurrence_cli

  hit = recurrence_cli._find_instance(entry_id)
  if hit is None:
    return 2  # not a rule instance: the caller reports the unknown id
  rule_hit, occurrence_date = hit
  if occurrence_date > recurrence_cli.TODAY():
    # future instance: interactive confirm — datum first, Enter keeps
    return recurrence_cli._confirm_instance(rule_hit, occurrence_date)
  return recurrence_cli.commit_instance(
    rule_hit,
    occurrence_date,
    occurrence_date,
    rule_hit.description,
    rule_hit.category,
    rule_hit.amount,
  )

def _confirm_instance(rule_hit: Recurrence, occurrence_date: date) -> int:
  """Confirm a landed rule instance as a real transaction: prompts prefilled
  with the instance's values (Enter keeps, 'q' aborts), then the shared
  commit core. Also the interactive path for FUTURE instances (from
  confirm.py): the date may shift DOWN to today, but a confirmed date in
  the future is refused — an actual never lies ahead of today."""
