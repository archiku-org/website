    3. Archetype mapping

    Rendered from narrative:archetype-mapping-financials v12 (agent-authored, produced-under task:19; describes → 10 components: ask-layer, config-layer, expected-register-store, interactive-add-flow, journal-core, journal-native-command-mutations, ledger-view-layer, recurrence-rule-engine, reporting-layer, tui-shell; full incoming links executed on the narrative).

    What kind of application this is. financials is a personal, journal-first personal-finance command-line application with a terminal UI: an append-only event-sourced money journal (component:journal-core) that every mutating command flows through (component:journal-native-command-mutations), with forecasting, grouping and reporting as projections on top — never as second stores of truth.

    Mutations vs transactions — identity vs integrity (concept:1). The journal stores mutations; their content-hash ids are rehash-verified on read, while a transaction's id is assigned once and never recomputed. The ledger is the fold of the journal (concept:2) — replay in append order into date-positioned transactions (business-rule:9) whose balances propagate forward; checkpoints serialize the fold, atomically (business-rule:6), and boot hydrates from checkpoint plus journal tail.

    Committed versus forecast. Three stores divide the world: the journal is the only record of committed money (concept:7); the expected register holds strictly future one-off rows (concept:6); recurrence rules expand virtually, never materialized (concept:9, non-goal:2). The open/confirm boundary is the hinge: a landed row (concept:21) becomes actual through a single ConfirmMutation that both retires the expected row and lands the actual (concept:8, concept:20).

    The typed id space (concept:22). t#### actual, e#### expected, g#### group, r:-hash rule instance — one id contract reused by edit, delete, confirm and group resolution (concept:27), with the resolver in business-rule:99 spanning all three member id families (concept:19).

    One composition, three renderings (component:ledger-view-layer). The projection composes actuals + expected + rule expansions (business-rule:75) with group rollups (concept:17), then serves list, the TUI shell (component:tui-shell — history, OPEN and PROJECTIE as one table; business-rule:87) and the reporting layer (component:reporting-layer).

    Interaction is prompted, bilingual, and abort-safe. The interactive add flow (component:interactive-add-flow) projects the new checking balance and makes the user acknowledge it (concept:15); the TUI add dialog (tui/add.py) reuses the CLI's validation rules rather than duplicating them; the shared category ask layer (component:ask-layer) and config layer (component:config-layer) define one approved-category list; every prompt loop aborts cleanly.

    Migrations are events too. The maintenance scripts (component:maintenance-scripts) moved legacy stores into the journal with the same transparency: explicit corrections instead of hidden reconciling entries (concept:34, non-goal:8), staging plus fold-verification before any write, and the no-reconcile op discipline the journal keeps to this day.

    4. Product summary

    Rendered from narrative:product-summary-financials v2 (kind: product-summary, audience: client, produced-under task:19). Structure and claims as captured; its business-rule basis was a deterministic sample of 50 of 148 business-rule facts.

    One command surface, safety by default. Eleven subcommands (add, expect, edit, delete, confirm, group, recurrence, list, tui, report, fix) dispatch with no business logic in the dispatcher; Ctrl-C in any prompting command cancels cleanly ("Geannuleerd, nothing saved"); approved categories and data directory come from a two-level TOML cascade.

    One-step confirmation. Bare confirm lists the OPEN section, then routes your id by shape (group / expected / rule instance / already-actual); an expected row commits only when landed and amount-bearing (business-rule:102).

    Plan the future without moving money. The expected register (concept:6) keeps one-off future entries (e#### ids) in their own store, posting no balances; rows must be strictly future-dated and approved-category (business-rule:30), and future-dated add input routes there automatically.

    Group the noise away. Groups roll related rows into one virtual view row, resolved across all three id families (business-rule:99); membership edits never move money or touch the ledger.

    Record money in seconds. add runs three paths — flagged, quick-add one-liner, bare interactive — over one shared validator (business-rule:24); the shorthand (concept:23) reads date/amount/Category:description with bilingual day words and sign-or-euro money markers; future-dated complete entries go to the expected register instead of the journal.

    Correct history with guides, not guesses. edit/delete resolve ids across the whole family chain with prefilled prompts and explicit typed confirmation ("ja" — bare Enter is never yes); un-grouping spares members; suppressing a rule occurrence keeps the rule running.

    Every change is journal-native. Each command becomes one mutation through the single write step — timestamp, content-hash id, append, tail replay, checkpoint (business-rule:12); history is append-only and replayable.

    See everything at once. The view composes committed history, actuals, OPEN, then PROJECTIE — expected entries plus virtual rule occurrences, visible until superseded by real rows or confirmed (business-rule:75) — one composition feeding list, the TUI shell and the report.

    Let patterns propose; you decide. Recurrence rules expand virtually into the projection and detection only prints proposals — rule creation always requires the explicit seeded review loop.

    Report the boundary-true record. Monthly overview, top-N category rankings, end-of-month balance curves in Dutch format; Overdracht transfers are excluded from flow totals but keep balance effects (business-rule:123).

    Where the boundary lies. Rules never materialize into the ledger (non-goal:2); groups are never journaled; reporting never reconciles; the journal has no account registry and no reconcile op — unexplained money was materialized as explicitly reviewed correction transactions; maintenance and migration scripts report by default, back up before writing, and retire superseded stores as timestamped backups — never delete.
