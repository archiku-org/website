    Functional Analysis - financials

    1. Executive Summary

    Scope. 75 modules, 26 components, 148 business-rules, 37 concepts, 7 processes, 9 non-goals, 11 surface commands — the analysis base this summary condenses (business-rules: deterministic sample of 50 of 148; all other payload families read in full).

    Archetype. An append-only journal-first finance CLI with a terminal UI: committed money lives only in a content-hash-integrity journal folded into a date-positioned ledger; forecasts (expected register, recurrence rules, groups) are projections that never themselves move money.

    Top capabilities. Three-mode quick add with balance-confirmation gate; one-step confirm of landed open rows (single retires-and-lands mutation); guided edit/delete across the full typed id space (t####/e####/g####/r:); virtual recurrence rules with human-gated detection; group rollups in the view only; a composed projection serving list, TUI and Rich reports with Overdracht-excluded flows.

    Non-goals that shape it. No reconcile/account-creation ops — accounts emerge from postings and unexplained money is an explicit reviewed correction; rules never materialize; groups never journal; reporting never reconciles.

    Start here. Read the product summary for capability-by-capability detail, then the archetype mapping for how the concepts live in the components; use financials list as the designated id source for anything edit/confirm/delete.

    Verification status. 4 objections are recorded in the vault by the verification phase and remain open — none are resolved in this engagement; read them before treating any claim above as final.

    3. Archetype Mapping

    financials is a personal, journal-first personal-finance command-line application with a terminal UI: an append-only event-sourced money journal (component:journal-core) that every mutating command flows through (component:journal-native-command-mutations), with forecasting, grouping and reporting as projections on top — never as second stores of truth.

    Mutations vs transactions — identity vs integrity (concept:1). The journal stores mutations; their content-hash ids are rehash-verified on read, while a transaction's id is assigned once and never recomputed. The ledger is the fold of the journal (concept:2) — replay in append order into date-positioned transactions (business-rule:9) whose balances propagate forward; checkpoints serialize the fold, atomically (business-rule:6), and boot hydrates from checkpoint plus journal tail.

    Committed versus forecast. Three stores divide the world: the journal is the only record of committed money (concept:7); the expected register holds strictly future one-off rows (concept:6); recurrence rules expand virtually, never materialized (concept:9, non-goal:2). The open/confirm boundary is the hinge: a landed row (concept:21) becomes actual through a single ConfirmMutation that both retires the expected row and lands the actual (concept:8, concept:20).

    The typed id space (concept:22). t#### actual, e#### expected, g#### group, r:-hash rule instance — one id contract reused by edit, delete, confirm and group resolution (concept:27), with the resolver chain in business-rule:99 spanning all three member id families (concept:19).

    One composition, three renderings (component:ledger-view-layer). The projection composes actuals + expected + rule expansions (business-rule:75) with group rollups (concept:17), then serves list, the TUI shell (component:tui-shell — history, OPEN and PROJECTIE as one table; business-rule:87) and the reporting layer (component:reporting-layer).

    Interaction is prompted, bilingual, and abort-safe. The interactive add flow (component:interactive-add-flow) projects the new checking balance and makes the user acknowledge it (concept:15); the TUI add dialog (tui/add.py) reuses the CLI's validation rules rather than duplicating them; the shared category ask layer (component:ask-layer) and config layer (component:config-layer) define one approved-category list; every prompt loop aborts cleanly.

    Migrations are events too. The maintenance scripts (component:maintenance-scripts) moved legacy stores into the journal with the same transparency: explicit corrections instead of hidden reconciling entries (concept:34, non-goal:8), staging plus fold-verification before any write, and the no-reconcile op discipline the journal keeps to this day.

    4. Product Summary

    One command surface, safety by default. Eleven subcommands (add, expect, edit, delete, confirm, group, recurrence, list, tui, report, fix) dispatch with no business logic in the dispatcher; Ctrl-C in any prompting command cancels cleanly ("Geannuleerd, nothing saved"); approved categories and data directory come from a two-level TOML cascade.

    One-step confirmation. Bare confirm lists the OPEN section, then routes your id by shape (group / expected / rule instance / already-actual); an expected row commits only when landed and amount-bearing (business-rule:102).

    Plan the future without moving money. The expected register (concept:6) keeps one-off future entries (e#### ids) in their own store, posting no balances; rows must be strictly future-dated and approved-category (business-rule:30), and future-dated add input routes there automatically.

    Group the noise away. Groups roll related rows (a card statement's purchases) into one virtual view row, resolved across all three id families (business-rule:99); membership edits never move money or touch the ledger.

    Record money in seconds. add runs three paths — flagged, quick-add one-liner, bare interactive — over one shared validator (business-rule:24); the shorthand (concept:23) reads date/amount/Category:description with bilingual day words and sign-or-euro money markers; future-dated complete entries go to the expected register instead of the journal.

    Correct history with guides, not guesses. edit/delete resolve ids across the whole family chain (actual, expected, group, rule occurrence) with prefilled prompts and explicit typed confirmation ("ja" — bare Enter is never yes); un-grouping spares members; suppressing a rule occurrence keeps the rule running.

    Every change is journal-native. Each command becomes one mutation through the single write step — timestamp, content-hash id, append, tail replay, checkpoint (business-rule:12); history is append-only and replayable.

    See everything at once. The view composes committed history, actuals, OPEN, then PROJECTIE — expected entries plus virtual rule occurrences, visible until superseded by real rows or confirmed (business-rule:75) — one composition feeding list, the TUI shell and the report.

    Let patterns propose; you decide. Recurrence rules expand virtually into the projection and detection only prints proposals — rule creation always requires the explicit seeded review loop.

    Report the boundary-true record. Monthly overview, top-N category rankings, end-of-month balance curves in Dutch format; Overdracht transfers are excluded from flow totals but keep balance effects (business-rule:123).

    Where the boundary lies. Rules never materialize into the ledger (non-goal:2); groups are never journaled; reporting never reconciles; the journal has no account registry and no reconcile op — unexplained money was materialized as explicitly reviewed correction transactions; maintenance and migration scripts report by default, back up before writing, and retire superseded stores as timestamped backups — never delete.

    Business-rule scope: narrated from a deterministic sample of 50 of 148 business-rule facts (first five ids, then every third id to 138); concept, component, non-goal and process families were read in full.

    5. Component Map

    Component: ask-layer

    Shared interactive category-prompting: ask_category returns one approved category, preferring questionary (arrow-key select + type-to-filter, j/k keys disabled because they conflict with the filter) when that package is importable, else a plain rich Prompt fallback with RETRY_LIMIT silent validation; both paths return the ABORT sentinel on user cancel.
    grounded in: file:src/financials/ask.py, task:15

    Component: Change-set fix engine

    Roadmap step 6 engine that applies reviewed fix files (change-sets) against the journaled ledger. THE single write path to the ledger: every op becomes a mutation appended via commands.append_and_apply (append → boot replay → checkpoint), so a guard violation aborts before any append and every journal line records a change that actually happened. apply_ops handles row ops (remove_row on ledger targets or e#### entries in the expected register, add_expected_row), apply_field_ops handles id+field+from+to fixes (each one from-guarded UpdateMutation with the final row state). apply_fixes loads a JSON fix file, dispatches to both, and runs the migration journal when one is present.
    grounded in: file:src/financials/fixes.py, task:6

    Component: checkpoint-regenerator

    One-time script that rewrites the migration staging checkpoint (migration/ledger.json) to the canonical fold of the staging journal. Dry-run folds the journal, prints tip balances, and diffs the existing checkpoint's entry ids against the fold's entry ids (reporting the first divergence row); --write backs up the checkpoint, regenerates it via financials.journal.checkpoint (atomic write), then verifies by hydrating from the rewritten checkpoint and comparing it exactly (ids + balances) to a fresh fold.
    grounded in: file:scripts/recheckpoint.py, subsystem:maintenance-scripts, task:16

    Component: CLI dispatcher

    The command-line entry of financials: one argparse main() that registers eleven subcommands (fix, report, add, expect, edit, delete, confirm, group, list, tui, recurrence), parses argv, and dispatches each command to a functional module (entry, expected, edit, delete, fixes, reporting, confirm, groups, ledger_view, tui, recurrence_cli). The module contains no business logic of its own: it translates arguments, delegates, and turns each handler's return value into the process exit code via raise SystemExit(handler(...)), while wrapping the four prompt-driven commands (add/edit/delete/confirm) in KeyboardInterrupt cancellation. Reached via the console-script entry point and the module main-guard (if name == "main": main()).
    grounded in: file:src/financials/cli.py, task:14

    Component: config-layer

    Runtime configuration for financials: a FinancialsConfig dataclass whose categories and data_dir are loaded from the clevis TOML cascade (user ~/.financials.toml + optional project ./financials.toml, no CLI layer), reached only through the cached accessor get_config(); exposes approved_categories() and expanduser'd data_dir(). The loader is isolated in config_loader.py specifically so tests can patch it in isolation.
    grounded in: file:src/financials/config.py, file:src/financials/config_loader.py, task:15

    Component: Confirm command

    The one-step confirmation fast path for landed-but-unconfirmed entries: bare confirm shows the ledger's OPEN section and asks which id to confirm; an id is then dispatched by prefix (g#### group / e#### expected row / r:-hash rule instance / otherwise a committed actual, which is a no-op). Expected rows commit zero-prompt via the ConfirmMutation path (cmd_add with retires, then the expected row is dropped) — the same path as edit's all-Enter confirm. Rule instances commit zero-prompt with the rule's own values when landed, or fall back to the interactive prefilled prompts when still future. Groups confirm every landed member in (date, id) order and re-point each retired e#### to its new committed id so the group survives. Exit codes: 0 confirmed/already-actual, 2 refused or nothing to do.
    grounded in: file:src/financials/confirm.py, task:13

    Component: expected-pollution-cleaner

    One-time cleanup script (2026-09-21) that removes the test-pollution rows that runs of tests/test_edit_move.py bled into the live expected.json. Rows are dropped only when both their id (e0092..e0099) and their content signature match exactly; matching is report-only until --write is passed, and expected.json is backed up before any write.
    grounded in: file:scripts/drop_expected_pollution.py, subsystem:maintenance-scripts, task:16

    Component: Expected-register store

    src/financials/expected.py manages one-off future entries in their own store (data/expected.json), separate from the journal: add_expected validates (must be future-dated, approved category, non-zero amount) and saves a STATUS_EXPECTED Transaction with eNNNN ids; fix files can re-create rows via add_expected_row_from_fix; list/remove round out the register CRUD. No balance posting happens here — balances start None until a confirmation retires the row into the ledger.
    grounded in: file:src/financials/expected.py, task:5

    Component: groups & rollups engine

    Named rollups of projected/committed rows (financials group): a group bundles related rows (credit-card statement purchases) into one virtual row in the view — members are e####, committed hash ids, or r: rule instance ids, and the statement shows as a single row with the summed amount on the rollup date. The module owns the Group dataclass, the groups.json overlay store, member-id resolution across the three id families, rollup-row construction, and the group CLI verbs (create/ add/remove/delete/edit/list/show).
    grounded in: file:src/financials/groups.py, task:12

    Component: Interactive add flow

    src/financials/entry.py implements financials add's three entry paths — fully flagged, shorthand-seeded, and fully interactive — with a shared validator (validate) and an interactive prompt loop (_prompt) that pre-fills from a parsed Shorthand, projects the new checking balance from the ledger's date-positioned predecessor, and verifies the user's balance confirmation against that projection with a 3-attempt retry limit. Future-dated full entries are date-based dispatched into the expected register (add_expected).
    _grounded in: file:src/financials/entry.py, task:5

    6. Concepts

    Concept: identity vs integrity

    Two distinct id roles in the journal (decdocs/journaled-ledger.md, 2026-09-18): a MUTATION's id IS its anti-corruption validator — a 16-hex sha256 content hash over the canonical mutation minus the id (rehashed on read). A TRANSACTION's id instead is identity, assigned ONCE by its creating mutation (add|confirm) and never recomputed; updates and balance propagation keep it, so linked/retired transactions never need rescanning. A transaction additionally carries a separate stored hash (content minus the hash field, balances included) that guards its row on disk.

    Concept: coverage window constants

    Window constants in the recurrences prelude compose the coverage/lookback semantics: AMOUNT_TOLERANCE = 0.01 (coverage amount match), DAY_WINDOW = 5 (days around the rule day that a covering transaction may sit), RULE_LOOKBACK_DAYS = 35 (the view's grace lookback before the ledger's anchor). All three are module-level literals consumed as literals by expansion and view code.

    Concept: anchor row

    The chronologically last committed ledger row on or before today, chosen by the chain-tip convention, whose calculated balances (checking and savings) seed the projection walk; when no committed row exists on or before today the anchor is None and balances project from a lookback before today instead.

    Concept: projection anchor

    The initial scroll position of the TUI ledger, anchored on the PROJECTIE separator row: that row lands at the bottom of the viewport with a fixed 10-line context window above it (_ANCHOR_CONTEXT_LINES), snapped so the top visible row is never cut mid-row. Because entry rows are two lines tall, the scroll offset is computed in LINES (summed per-row heights) not rows; only this initial positioning uses line math — cursor, keys and dialogs stay row-based.

    Concept: entry kind

    The row's provenance label shown in the detail dialog's status line — where the entry came from in the view's composition: KIND_COMMITTED "journaal-geboekt" (history band or actuals window), KIND_OPEN "openstaand (geland, niet bevestigd)", KIND_PROJECTED "projectie (verwacht door regel)". Kept as parallel per-entry state (_entries maps id → (entry, checking, savings, kind)).

    Concept: form-walk

    The add dialog's navigation discipline: Enter (or completing the category dropdown) advances focus through the fixed field order Datum → Omschrijving → Categorie → Bedrag → checking-saldo; on the last field (saldo) Enter submits the form. Tab also works natively. Later-dependent state (the saldo projection) is refreshed on Enter for the date and amount fields before advancing.

    Concept: saldo confirmation gate

    The fifth add-form field (Checking-saldo): the user is shown the live projection of the checking balance for the typed date+amount and must acknowledge it. Blank accepts the projection; a typed value must match it within a cent. The gate is "you saw the number" — the typed value is never stored. When no predecessor row exists there is no projection and the gate is skipped. On a future date the field instead carries the expected-register marker (no balance chaining).

    Concept: questionary-style autocomplete

    The category dropdown behavior the add dialog mimics from questionary: the FULL approved-category list is offered the moment the field takes focus (an empty input shows all candidates), typing narrows fuzzily. Implemented by overriding both should_show_dropdown (visible whenever any candidate exists, not only on a non-empty search string) and _handle_focus_change (focus alone routes through _handle_target_update to align + rebuild + show; blur hides).

    Concept: group rollup

    A virtual Transaction standing in for a group's members at render/walk time in the ledger view: members are hidden and replaced by one row (id g####, description 📁 label (count), amount = member sum) — a view-time projection only, member rows keep their own ids and stores.

    Concept: dangling member

    A group member id that no longer resolves through any id family (resolve_member returns None) or has a null amount: the group show renders it in a dedicated dangling warning and excludes it from the total.

    7. Business Rules

    business-rule:1

    Updating a transaction is composed as delete followed by insert: the transaction's id (assigned at creation) rides along so linked references elsewhere stay valid, and balances re-derive through the propagation of both steps.

    implemented in: src/financials/journal.py:227-235

    business-rule:10

    Checkpoint hydration does not re-fold: balances are first-class snapshot state carried by the rows; hydration rebuilds transactions from the rows and verifies only their hash guards. Bare rows from bootstrap-era checkpoints (no hash guard) are accepted; guarded rows failing verify() are refused loudly.

    implemented in: src/financials/journal.py:158-175

    business-rule:100

    The rollup row for a group has id = the group id (g####), description formatted as an emoji-flagged label with the member count, amount = the member sum rounded to 2 decimals, status inherited from the first member row, and its rollup date is the group's own ISO date when set, else the members' max date.

    implemented in: src/financials/groups.py:184-189, src/financials/groups.py:192-205

    business-rule:101

    Group ids are minted as g#### by scanning all existing groups for ids matching g + digits and taking the highest numeric suffix plus 1, zero-padded to four places.

    implemented in: src/financials/groups.py:74-79

    business-rule:102

    Confirming an expected row refuses a row dated in the future and refuses a row with no amount (exit 2, nothing applied); only a landed, amount-bearing row commits.

    implemented in: src/financials/confirm.py:68-76

    business-rule:103

    A confirmed expected row commits as one ConfirmMutation (cmd_add with retires=[e-row id]) and the expected row is dropped from the expected store only after the commit applied — never before.

    implemented in: src/financials/confirm.py:44-61, src/financials/confirm.py:77-84

    business-rule:104

    Confirming a group id confirms only LANDED members (resolveable, not future, not already actual, amount-bearing) in (date, id) order; future, dangling and amount-less members are skipped with a note and the group survives; nothing confirmable exits 2, a partial confirm still exits 0.

    implemented in: src/financials/confirm.py:125-131, src/financials/confirm.py:141-158

    business-rule:105

    After an e#### member commits inside a group confirm, the membership list is re-pointed from the retired e-id to the new committed hash id, reloading the group file after every save because resolve_member reboots the journal.

    implemented in: src/financials/confirm.py:161-170

    business-rule:106

    A rule-instance member within a group confirm is skipped when an existing actual ledger entry already covers it — same category, a checking posting within AMOUNT_TOLERANCE of the rule amount, and a date within DAY_WINDOW of the occurrence — preventing double commits of superseded instances.

    implemented in: src/financials/confirm.py:181-192

    business-rule:107

    Confirming an id prefix-dispatches: g#### with digits → group confirm, e#### with digits → expected-row confirm (unknown id → exit 2), r:-prefixed → rule-instance confirm; anything else resolves against the committed ledger where an already-actual entry is a no-op (exit 0) and an unknown id exits 2.

    implemented in: src/financials/confirm.py:242-261

    12. Non-Goals

    non-goal:1

    Statement: The journal has no opening op: opening balances are represented as ordinary add transactions, and the first posting to an account implicitly creates the account — there is no separate account registry or account-creation step in the journal core (module docstring, src/financials/journal.py lines 23-24).

    Rationale: Stated in the module docstring; accounts are an emergent property of postings rather than first-class objects.

    non-goal:2

    Statement: Recurrence rules are never materialized into the ledger: the module docstring states this design invariant, and expand_recurrences realizes it by synthesizing ephemeral virtual Transaction objects with status "expected" at expansion time rather than writing recurrence rows into stored ledger data.
    Rationale: Anchored in the module docstring (src/financials/recurrences.py:1) and the virtual-synthesis body of expand_recurrences (src/financials/recurrences.py:147-182); virtual instances exist only in memory for views and confirmations.

    non-goal:3

    Statement: The recurrence CLI does not create rules automatically from detection — detection only prints proposals; rule creation always requires the explicit user approval of the seeded field loop (or fully-flagged add).

    Rationale: The docstrings state it explicitly ('NOTHING is created'; 'the proposal alone never creates a rule') — recurring money movement is trusted only to a human-reviewed rule. Evidence anchors: src/financials/recurrence_cli.py:855-857 and 915-918.

    non-goal:4

    Statement: The ledger TUI does no offset/scroll math for cursor movement or dialogs — the DataTable clamps at the first/last row and auto-scrolls the viewport itself by row; only the initial projection-anchor positioning uses line-based scroll math (rows are mixed-height, so that one case needs line offsets).

    Rationale: Stated verbatim in the module docstring ('The DataTable clamps at the first/last row by itself (no offset math here)… only the initial-position scroll math needs line offsets') and honored by the code: _focus_row and _position_at are the only scroll computations, both called with call_after_refresh.

    non-goal:5

    Statement: Groups are not journaled and never move money: the projection hides members and rolls them up at render/walk time only, group add/remove edit only the membership list and leave the member rows untouched in their own stores.

    Rationale: Journal = committed money; expected + rules + groups = forecast inputs. Keeping groups outside the journal keeps the committed ledger authoritative and membership reversible.

    non-goal:6

    Statement: Confirm never commits a FUTURE rule instance itself: a future occurrence is handed to recurrence_cli's interactive prefilled prompt walk, and recurrence_cli's own future-date gate refuses an actual dated ahead of today — confirm does not bypass or duplicate that gate.

    Rationale: The module reuses recurrence_cli._confirm_instance for future instances (confirm.py:111-113) and its docstring states the gate belongs to recurrence_cli; keeping one date gate avoids two diverging validation paths.

    non-goal:7

    Statement: The reporting layer does no reconciliation or anomaly detection: it renders aggregated totals and balance curves as recorded; it never validates that summed flows match balance deltas (no flag-based or balance-mismatch logic lives in reporting).

    Rationale: Balance-mismatch flags exist in the model (FLAG_BALANCE_CHECKING / FLAG_BALANCE_SAVINGS) but reporting only reads balances for display; checking is deferred to other layers.

    non-goal:8

    Statement: The journal op vocabulary deliberately has no reconcile operation (nor an opening op): money that moved without a transaction is never silently reconciled — it becomes an explicit correction transaction, listed for owner review.
    Rationale: Owner policy 2026-09-18: "I will always create a transaction implementing the mutation" — hidden reconciling entries would defeat the journal's auditability, so the maintenance tooling derives explicit correction rows instead.

    non-goal:9

    Statement: The maintenance scripts do not silently destroy superseded data: retired stores are preserved (timestamped .retired backups), refused rows are always reported for owner decision, and nothing is ever guessed away.
    Rationale: None

    13. Appendix: Quirks

    quirk:1 (lineage)

    Description: remint() is a repair pass kept in the core module: it re-mints the ids of journal rows whose stored id no longer matches their content hash — a legacy of a 2026-09-19 writer bug where ts was written into the line but the id was minted before ts became hashed content (four live observer rows). Only affected lines are rewritten, byte-preserving the rest; a dry_run mode reports without writing. It exists so old journals stay foldable under the current hashing rules.

    Parity Relevance: A parity implementation must decide whether remint's repair semantics (re-derived ids, line-level rewrite, dry_run report shape) are normative or historical-only; replaying the same legacy journal must produce the same repaired ids either way.
    Impact: src/financials/journal.py:413-446

    quirk:10 (integrity)

    Description: _resolve_ledger_target matches a fix id as 'full hash id OR t.id.startswith(fix_id)' — a prefix match, not a word-boundary match. A fix id that is a prefix of another transaction's id does not merely risk ambiguity: _load_fixes_file and the fix-file format invite hand-written short ids, where full-hash vs short-prefix is indistinguishable. Ambiguity raises only when MORE THAN ONE row matches; a unique prefix silently wins, and a one-character prefix of a unique hash is a legal target.

    Parity Relevance: Parity fixtures should use full hash ids; a single-char prefix may resolve to a different row in a different dataset and silently apply the fix to the wrong transaction.
    Impact: src/financials/fixes.py:61-69

    quirk:11 (parity)

    Description: fixes.py defines and exports GLOBAL_OPS = {'remove_row', 'add_expected_row', …} in all, but no other file or symbol references it. It is a vestige of the pre-journal global-op engine: the journaled change-set now refuses global ops outright (fix_id 'all' raises ValueError in both apply_ops and apply_field_ops).

    Parity Relevance: Parity work should not reproduce the GLOBAL_OPS export surface; the live behavior is that global ops are refused, not dispatched.
    Impact: src/financials/fixes.py:55, src/financials/fixes.py:274

    quirk:12 (parity)

    Description: Monthly and yearly expansion silently skips impossible calendar dates: when the rule's day does not exist in a month (day 31 in a 30-day month, Feb 29 in non-leap years), push() swallows the ValueError and that month produces no occurrence; the next month resumes normally. No error, warning, or substitute date is emitted, and monthly rules default to day 1, yearly to month 1/day 1, when unset — the "one instance per month" reading of a rule is subtly false for day-29/30/31 rules.

    Parity Relevance: Any parity reimplementation must reproduce the exact skip-not-shift behavior; shifting to the next valid date instead would change which months expand and alter both virtual ids and coverage windows.
    Impact: src/financials/recurrences.py:69-89

    quirk:13 (forecast)

    Description: Tier B detection deliberately has NO magnitude guardrail: budget-style series (the owner confirms a fixed budget with the actual spend) vary far more than 2x between occurrences, so rejecting large spreads would kill real patterns; instead the observed [min, max] spread is surfaced honestly as amount_range on the proposal. The trade-off is accepted because proposals are review-only — a noisy proposal costs a glance, not an automatic rule.

    Parity Relevance: A parity implementation adding an intuitive "amounts differ too much" rejection would diverge: proposals the reference detector emits must keep being emitted even with wild amount spreads, as long as dates classify and signs are uniform.
    Impact: src/financials/recurrences.py:236-239

    quirk:14 (naming)

    Description: RETRY_LIMIT = 3 is defined at module level (line 42) but never used anywhere in the file — it reads like a leftover from an earlier retry prompt design. Everything else in the module is wired; this is the only dead symbol in the covers.

    Parity Relevance: Harmless for parity, but a parity port that treats it as meaningful retry behavior would invent behavior that does not exist.
    Impact: src/financials/recurrence_cli.py:42

    quirk:15 (format)

    Description: The weekly cadence confirmation after a successful add prints a doubled opening parenthesis — 'wekelijks ((ma))' — for frequency weekly, while the biweekly branch prints the single-paren form 'tweewekelijks (ma)'. A cosmetic format slip in the success message, not the data.

    Parity Relevance: A parity harness diffing success-line output would flag 'wekelijks ((ma))' as a mismatch; the doubled paren is in the reference output, not a bug to fix away.
    Impact: src/financials/recurrence_cli.py:469-472

    quirk:16 (forecast)

    Description: Projection windows are hard-coded in multiple shapes: _next_instances scans in 400-day chunks (window_end = TODAY() + 400 days), _find_instance projects through today + 400 days, and the lookback uses RULE_LOOKBACK_DAYS from the engine module. The 400-day forward horizon is a magic number, not a named constant; it silently bounds how far 'komende' dates and instance resolution can reach.

    Parity Relevance: A parity port must reproduce the 400-day horizon to match projected instance lists and confirm/edit resolvability for far-future instances.
    Impact: src/financials/recurrence_cli.py:75-77, src/financials/recurrence_cli.py:590

    quirk:17 (lineage)

    Description: The view layer hosts the canonical-journal boot (command_journal), whose docstring still speaks of a pre-promotion migration staging journal: a one-time data-migration mechanism lives on inside the view composition path used by every view command and the projection spine, long after the migration itself.

    Parity Relevance: A parity port may not realize the view boot is promotion-aware; porting only the data-journal boot would break environments that still have the migration staging journal.
    Impact: src/financials/ledger_view.py:37-51

    quirk:18 (format)

    Description: _fmt renders amounts in a Dutch-style format by round-tripping the thousands separator: f"{value:,.2f}" then replacing commas with X, dots with commas and X back with dots (line 96-99). The byte-exact output and the '—' em-dash for None values are part of rendered table text.

    Parity Relevance: Byte-parity on rendered tables requires reproducing this exact separator dance and the em-dash placeholder; a locale-aware formatter will not match.
    Impact: src/financials/ledger_view.py:96-99

    15. Sensitivity

    sensitivity:1

    Boot-time corruption policy splits responsibilities: content-hash mismatches in either journal rows or checkpoint rows are refused loudly (ValueError), truncation/reordering is explicitly NOT the hash's job — a checkpoint tip that never appears in the journal refuses boot with a message deferring structural damage to "the tip + backup path". The checkpoint's failure direction is always replayable (journal ahead of checkpoint), never silent data loss.

    Found in: src/financials/journal.py:483-488, src/financials/journal.py:526-531, src/financials/journal.py:450-458

    sensitivity:10

    The add dialog bypasses entry._validate's future-date rejection by dispatching to add_expected BEFORE calling _validate for past dates. Any refactor that reorders _submit's steps would push future-dated rows into the journal path and let _validate reject them (or worse, break dispatch parity) — the ordering between dispatch and validation is the load-bearing detail, mirroring the CLI's own dispatch-before-validate order.

    Found in: src/financials/tui/add.py:332-364

    sensitivity:11

    The TUI add screen imports the CLI's private validation internals (_validate, _validate_amount from financials.entry) as its rules source of truth. Renames/signature changes of those underscore-private functions break the dialog silently at import time; conversely, the dialog is the place where those rules must be kept visible — inline error text is TUI-specific but the RULES must never be duplicated locally.

    Found in: src/financials/tui/add.py:51-54, src/financials/tui/add.py:326-337

    sensitivity:12

    The last-resort member resolver recomputes recurrence expansion over a wide window (lookback + 60 days past, 400 days future) and re-hashes each active rule's instances to match a dangling member id — content hashes make instance ids edit-sensitive: a rule edit re-mints ids, so group membership silently references stale ids and resolution drifts onto whichever rule instance currently hashes to that id.

    Found in: src/financials/groups.py:143-157, src/financials/groups.py:167-178
