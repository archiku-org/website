    Issues & Hotspots

    1. Issues

    Note

    While analyzing the codebase, our agents often encounter issues. Although not strictly part of the analysis, we report them because they often hold valuable information where the current implementation fails.

    We identify four kinds:

    • code-bug: the implementation has a mistake that hinders the intended functionality
    • docs-drift: the documentation does not match the implementation and the documents are the stale side
    • docs-code-conflict: the mismatch is demonstrated but neither side is attributable yet
    • functional-mistake: the implemented behavior contradicts the established functional facts with no documented claim involved

    Financials add help offers a checking-balance flag the intake ignores

    Classification: docs-code-conflict

    Summary: The command's own help advertises "New checking balance (defaults to the continued balance)" for --checking, but the value is passed through and never used — a recording can never carry a hand-stated balance.

    Claim: New checking balance (defaults to the continued balance).

    Rationale: Read the dispatcher's add wiring (cli.py main, add branch) and the intake call chain (add_transaction entry.py:181-287). The claim comes from the add parser's own --checking help text (cli.py:80-85). Tracing the flag's value: args.checking is forwarded to add_transaction(checking=...) at cli.py:283; a syntactic reference search of entry.py shows checking appears only in _prompt internals (108, 112, 167, 171, 172) and the unused parameter declaration (186) — the parameter's value is never read anywhere in the function body. So a caller-supplied balance cannot influence any stored balance, contradicting the advertised "new checking balance" behavior. Neither side is trivially the stale one — the derived-only balance design at the confirmation gate (entry.py:160-177) may be what stranded the flag; both the help and the code stand coherent internally, so the conflict is parked for review rather than attributed.

    Financials add help undersells the shorthand grammar

    Classification: docs-code-conflict

    Summary: The command's help claims the quick-add slot order "[date] [amount] [Category:]description", but the parser also accepts relative day words and dates/amounts only in that fixed first-two slots — wordier than advertised, yet stricter elsewhere.

    Claim: Quick-add: "[date] [amount] [Category:]description" (date: ISO / vandaag / gisteren / morgen / -3d).

    Rationale: Compared the dispatcher's shorthand help (cli.py:91-98) against the traced parser (shorthand.py:101-138). The grammar promise "[Category:]description" is right about slot ordering and the day words. The gap: the parser only promotes the colon-headed part to the category when it canonicalizes against the approved list (shorthand.py:132-137); otherwise the whole remaining text is description. The help never states that the head must be an approved category — a bookkeeper typing "Winkel: brood" gets category=None and is prompted, reading the help as a contract. Neither side is plainly stale: the parser's behavior is deliberate (conservative resolution, docstring states it), and the help condenses it wrongly. Parked as a conflict for review.

    Bare confirm help text omits group ids the command actually accepts

    Classification: docs-code-conflict

    Summary: The confirm command's help promises plan ids and rule instance ids, but the dispatch also confirms group ids with their own path — the help text and the accepted id families diverge.

    Claim: "Confirm an open entry in one go: a landed expected entry (e####) or rule instance (r:...) commits as-is, zero prompts. Adjust first: 'financials edit'. Bare confirm shows the OPEN section."

    Rationale: Read the confirm parser definition (cli.py:140-153): the id argument's help names only expected entries and rule instances. Read the dispatch (confirm_transaction, confirm.py:232-261): the first branch tests the group family and routes to the group walk, which is real confirmed behavior (I traced the group walk in confirm.py:124-202 this engagement). Consulted: the surface command fact (financials-confirm), the group confirmation rule, and the group entity. The claim is verbatim from the help string; the code demonstrably accepts a third id family the claim never mentions — a demonstrated mismatch; attribution (help drift vs intentionally hidden feature) is not decidable from the code.

    Group confirm covered-skip note claims a booked row settled the member even when the member is a plan

    Classification: functional-mistake

    Summary: The covered-instance skip note is worded as if a booked row already settled the member; in the group loop the same covered logic also applies to rule-instance members only — but its dim wording suggests settledness the view may not show.

    Claim: {member_id} is al gedekt door een geboekte rij — overgeslagen.

    Rationale: Consulted the group confirm loop's covered test (confirm.py:183-189) against the projection's covering test (recurrences.py:110-125): the confirm path requires a checking posting and compares the posting amount; the projection's test compares amount_eur with no posting requirement and year-matches the date prefix. The skip message (string-literal, confirm.py:191) asserts settledness in the projection's vocabulary while the group path uses a different test. No docstring or help claims the two tests agree, so this is a functional discrepancy between two implementations, not a documented-claim conflict; per the family's boundary law it is recorded with the vocabulary-only class and stays out of my emission set as a side-class — flagged for review instead.

    Edit help omits that bare edit also reaches plans, groups and rule instances

    Classification: docs-code-conflict

    Summary: The command help says the id argument picks from the last ten actual rows when omitted — and the resolver does that — but the help never mentions the future-plan register, group-editor or occurrence-editor branches the bare path and unusual ids reach.

    Claim: Id from 'financials list' (omit to pick from the last 10 actual rows).

    Rationale: Consulted the argparse help text at cli.py:113-123 (the claim verbatim at :122), the edit resolver at edit.py:274-319, and the picker at edit.py:123-138. The help states the two documented paths verbatim; the resolver demonstrably accepts e#### (routes to _edit_expected at :304), g#### (edit.py:288-293) and r:… ids (edit.py:298-301), and the bare path filters rows to today-or-earlier before slicing the last ten (:127-128) — so the bare list truly holds only actual rows, matching the help's wording, but the id side of the help never mentions the plan, group or instance surfaces. Neither side is attributable — the help is not wrong about what it says, the resolver is not wrong about what it does; classified docs-code-conflict and left for review.

    Module docstring promises unambiguous-prefix id resolution the resolver never performs

    Classification: docs-code-conflict

    Summary: The delete module claims full and prefix id matching on committed rows; the actual ledger lookup is exact-match only, so a prefix quietly reports "Onbekende id".

    Claim: Resolves the id in the committed ledger (hash id, full or unambiguous prefix) or the expected register (e####), shows the row, and requires an explicit confirmation (bare Enter is NOT yes).

    Rationale: Consulted the module docstring as the claim, the ledger's own lookup (journal.py find, 177-185) which enumerates and compares each stored row's id for exact equality with no prefix handling anywhere on the delete path, the delete dispatcher (delete.py:105-143) which passes the typed id straight into that lookup, and the group resolver (groups.py:82-102) which alone implements prefix and name matching — for groups only. No prefix matcher for ledger rows was found on the traced path, and query_references shows no 'startswith' under delete.py at all. The claim's falsity is demonstrated on the code side; which side is wrong (stale docstring describing an older behaviour, or a promised feature never wired) cannot be decided from code alone, so the conflict stays unattributed.

    Recurrence add help names only monthly and yearly while add accepts all four cadences

    Classification: docs-code-conflict

    Summary: The command parser's own help for the frequency flag undersells the surface — weekly and biweekly rules (with their weekday anchor) work, including through the seeded editor, but the help says "monthly | yearly (add)".

    Claim: monthly | yearly (add)

    Rationale: Consulted the --frequency help string at the parser (cli.py:248) as the claim; against it, the validation gate (recurrence_cli.py:160-161) which enumerates monthly|yearly|weekly|biweekly as the accepted values on the very same add path, the add function's weekday handling (recurrence_cli.py:400-410) which asks and snaps anchors for weekly/biweekly, the module's dataclass comment (recurrences.py:30) listing all four frequencies, and list/confirm outputs renderingweekly and biweekly. Weekly and biweekly demonstrably work on the add path, so the help omits supported values. Which side is wrong — stale help or an intended flag-time restriction the code forgot to enforce — is not decidable from the code; left unattributed for review.

    The retry limit constant sits defined but unread in the recurrence module

    Classification: functional-mistake

    Summary: The recurrence command module defines a retry limit constant that nothing in the module reads — the three-retries discipline lives in other modules' own copies, and this one is dead weight on the rule surface.

    Claim: RETRY_LIMIT = 3

    Rationale: Consulted the constant definition at recurrence_cli.py:42 and the name trace across the codebase: every use of RETRY_LIMIT sits in entry.py, edit.py and ask.py, which define their own copies for their prompt-retry loops; the recurrence module's identifier appears exactly once — the defining line itself (query_references and query_callers agree, zero in-module reads). Dead on this surface, but no documented behaviour claim is involved, so recorded as a functional note rather than a claim-based divergence; the review phase may prefer deleting the line.

    Design doc names a balance-rebase helper in the fix engine that the code no longer has

    Classification: docs-code-conflict

    Summary: The ledger design log's step-6 section names rebase-checking-side logic as living in the fix engine file, but no such function exists anywhere in the codebase.

    Claim: rebase_checking (fixes.py) already implements the replay rule

    Rationale: Consulted: the design log step-6 section around the claim (docs/journaled-ledger.md, retrieval filtered on rebase/fixes), the fix engine's full symbol inventory (outline listing 11 symbols, file lines 61-274) — no symbol resembling a balance-rebase helper exists there — and a repo-wide name search returning zero occurrences. The claim is a specific, verifiable existence assertion; its failure is demonstrated. Attribution fails both ways: the doc carries dated design-decision marks but no explicit removal note for this helper, and the current update-as-rebook design (rule fact: a committed correction rebooks the row) makes the helper plausibly obsolete rather than missing-by-mistake. Classification therefore stays at the demonstrated state: the mismatch is real, neither side provably stale or buggy.

    2. Hotspots

    Note

    Sometimes our agents encounter a bump in the road, an implementation that is so obscure or a comment that is so incomprehensible, that they need your ruling to make sense out of it.

    These situations are reported as hotspots because they probably cover a dark secret that, when resolved, not only improved the analysis, but might also help to improve the implementation if needed.

    In contrast to issues, hotspots deal with functional uncertainty, yet the answer to their questions might result in a new issue.

    Whether a balance correction override is wanted

    Summary: The confirmation loop can only confirm or cancel; there is no saving path when the bookkeeper disagrees with the projection. Whether that is intended policy or a missing feature is a business decision the code cannot answer.

    Description: When a spend was actually made from a cash stash or an unlisted account, the real checking balance after it differs from what the books will project. The intake's confirmation loop offers exactly two endings: accept the projected figure, or have the recording cancelled after three attempts — a deliberate "the balance is really X" cannot be recorded. There is no policy text in the code or docs stating whether the household wants balances strictly derived (derived-only) or an override door for reconciliation. The behavior is coherent and the code decides it; the intent behind it is business-decided.

    Question: Should the household ever be able to save a recorded movement whose balance they know to differ from the projected books balance — a deliberate balance correction — or is refusing to record-on-mismatch the intended policy?

    Whether the checking-only preview is the intended projection

    Summary: The confirmation gate projects and confirms only the checking side, while a transfer recording also moves savings; whether the confirmation should mirror that is a business question, not decidable from code.

    Description: The intake's confirmation loop works the checking account only: the projection shown, typed and matched is checking-only. The posting rule, however, moves two accounts for a transfer (checking in, savings out — mirror). A bookkeeper confirming a transfer's checking projection is never asked about the savings side. The code offers no evidence of the intended policy: is savings implicitly trusted to follow the mirror, or is its omission at the gate a gap? The behavior is observable; the intent is not.

    Question: Should the pre-save projection confirm the checking balance only, or should it also account for savings — e.g. when the recording is a transfer the household considers as touching both accounts?

    Whether the parked --checking flag should be fixed or retired

    Summary: The advertised flag does nothing; whether the intended fix is an override path or a removal of the promise is a product decision the code cannot answer.

    Description: The dispatcher passes --checking into the intake and the intake ignores it; the help text still promises a "new checking balance". Two coherent readings exist: the flag is a leftover from a pre-derived-balances design and should disappear (aligning with the derived-only confirmation gate), or the balance-override door should be finished (aligning with the help). The code shows the current state but not which direction the household wants — a business call, made with the balance-override hotspot.

    Question: Should the --checking flag on financials add actually set the recording's starting balance, or should the unused flag (and its help promise) be removed so the surface no longer advertises a balance override the intake refuses?

    Group confirm exit codes report partial success as full success

    Summary: A group confirm that confirms some members and skips others exits 0; only a group with nothing landable exits nonzero — the code's choice, not the business's, is unrecorded anywhere.

    Description: When a group is confirmed, future-dated, amountless, unresolvable and already-covered members are each skipped with a on-screen note, while landable members commit; the command then exits as a success. Only the case where nothing at all could be confirmed exits nonzero. The code makes this choice consistently, but nothing in the help text or documentation states that "some members skipped" counts as success — whether that is the intended business signal (e.g. because the notes are enough for a human) or an unconsidered default is not decidable from the code. The answer lives with the business, not the analysis.

    Question: Should the confirm command report a partially-confirmed group as success (today's behavior — exit 0 with skip notes), or should the skipped members surface as a distinct failure-like signal so pipelines and scripts can react?

    The interactive instance confirm books real values the rule no longer knows

    Summary: The interactive path lets the bookkeeper shift the date and amount of an instance's confirm; the code then records an exception so the projection does not linger — but whether the rule's standing pattern should absorb the change is nowhere answered.

    Description: The interactive instance confirm exists so an early-landed bill (or one with a different real amount) can be confirmed with its real values. The commit then finds the values no longer cover the rule's period and records the occurrence date as an exception. That keeps the view honest, but it means the standing rule drifts from reality: the following month the rule again projects the old pattern day and old amount, while the household has now paid differently once. Whether the business wants the rule edited (so future instances adopt the new reality) or accepts a one-off exception (the bill was just odd) cannot be determined from the code — the code only implements the exception path. The answer lives with the business, not the analysis.

    Question: When the interactive confirm of a rule instance changes date or amount so the booking drifts outside the rule's covering window, should the rule itself be adjusted (its pattern day or amount updated to match reality), or is only the one-off exception date the intended outcome?

    Should the failed move rebuild or refund the deleted actual row

    Summary: The delete-first sequencing leaves a bookkeeper-visible hole — whether an automatic undo belongs there is a business decision, not decidable from the code.

    Description: The move route removes the committed row first (edit.py:214) and creates the planned entry second (edit.py:218). When the second step rejects, the row exists nowhere — the code prints the recovery hint naming the expect command and stops. The deletion is a journaled mutation, so a rebuild would be a new mutation sequence (a re-add), possible to compose — the question is whether the business wants silent self-healing of a failed move, or prefers the current explicit human recovery. The answer lives with the business, not the analysis — the code alone cannot say whether that behavior is intended or just the current sequencing.

    Question: When the move-to-expected deletes a committed row and the planned replacement then fails to save, should the code automatically rebuild the original actual row instead of leaving recovery to the bookkeeper?

    The expected register has two removal doors with different safety

    Summary: The delete command always asks before removing a planned entry; the standalone expected-entry removal never asks, and the code shows no evidence of which behaviour is intended.

    Description: There are two paths to strike a planned entry: the delete command (row printed, typed confirmation required) and the standalone expect-removal surface (silently removes by id, no prompt whatsoever — the only removal path in the codebase with no confirmation). Which is deliberate and which is an oversight is not decidable from the code: the standalone path's docstring and help text both claim a plain remove without warning, so the claim is at least self-consistent there; yet the household's other removal surfaces all enforce the confirm-first law, and a typo'd id removes a plan in one keystroke on this path. The business must decide which policy owns planned-entry removal.

    Question: Should a planned entry be removable without an explicit typed confirmation through the expect-removal surface, when the delete command's whole design says every removal asks first?

    The bare delete picker's date filter reaches rows beyond its purpose

    Summary: The picker filters menu rows by date rather than by kind — its effect on today's or past-dated non-committed rows is not decidable from the code.

    Description: The bare delete command shows a pick menu built from the ledger view's rows, keeping only rows whose date is not in the future. The intent the docstring names is a menu of past actual rows, and on today's data committed rows are past-dated, so the behaviour looks right — but the filter reaches anything with an old date, whatever its kind, and the ledger view's row list is the composed view, not the raw committed list. Whether a kind check was intended, or the date window is deliberate (perhaps to let transfers dated today appear), is a design question the code cannot answer — the business owns which reading is meant.

    Question: Should the bare delete picker only ever offer committed past rows (a kind check) rather than filtering by date, which reaches any row dated today or earlier?

    Whether the two-month gap should classify a monthly pattern

    Summary: The gap bands make a skipped month (gap ~60 days) fail every band, so a seasonal-but-mostly-monthly bill is never proposed; whether that is the intended strictness is a business call.

    Description: The classifier accepts a cadence only when enough consecutive gaps fall inside its band; a monthly band spans 26–38 days, so a single skipped month produces a gap of about 60 days that matches nothing. The weekly band has an explicit tolerance for one skipped week (the band overlaps biweekly's), but the monthly band has no such slack — one missed month kills an otherwise long monthly streak for proposal purposes. The code shows what the threshold currently does; whether the business wants a mostly-monthly but occasionally-skipped bill (someone on holiday, a waived fee) to surface as a proposal is not decidable from the code. The answer lives with the household's owner, not the analysis.

    Question: Should a repeating payment that skips one month entirely — a gap of roughly sixty days inside an otherwise monthly streak — still be recognized and proposed as a monthly rule, or is silence the intended behaviour for months the pattern did not appear?

    Sweep order sorts file names, not review sequence

    Summary: The pending sweep orders files by name; whether that reliably equals review order depends on the bookkeeper's file-naming convention, which the tool does not enforce.

    Description: The sweep sorts pending cleanup files by their names and applies the first name first, presenting this as oldest-first. The intent is that corrections reach the ledger in the same order the reviewer produced and reviewed them. But nothing in the code ties a file's name to when it was authored: the oldest-first claim holds only if the bookkeeper names files so that name order encodes time (dates in names). No surface communicates or validates that convention. Whether names-in-date-format is an assumption the business is willing to live with — versus a stated naming convention the tool should check — is a question for the people running the process.

    Question: Should the sweep's oldest-first order follow the file names' alphabetical order, or should it follow the order in which the reviews happened when names share a timestamp convention that alphabetical order does not reflect?

    Reviewer remarks never reach the permanent record

    Summary: Fix files carry a free-text reason per fix, shown only while the change-set runs; nothing stores it beyond that print and the applied file's content on disk.

    Description: The cleanup tables printed during application show each fix's stated reason beside each change. The reviewer wrote those reasons as part of the reviewed file. They are not recorded anywhere in the system's own stores: the change journal carries only the corrected row states (never the reasons), and nothing else persists them. The only surviving trace is the applied file itself sitting renamed on disk. Whether that is the intended division — the file is the review record and the system's journal is the execution record — or the reasons ought to ride into the permanent record for auditors, is a business decision the code cannot make.

    Question: Should the reason text a reviewer attaches to each fix be preserved in the permanent record, or is the change journal alone the intended audit trail of record?
