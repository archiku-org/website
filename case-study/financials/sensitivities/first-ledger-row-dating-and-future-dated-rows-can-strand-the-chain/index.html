Title

First-ledger-row dating and future-dated rows can strand the chain

Sensitivity Statement

An actual entry dated before the ledger's first row cannot be saved, and warning only inside the prompt is easy to miss — a future-dated confirmation rows further out the more the ledger grows.

Summary

The chain has a hard start (no predecessor, no save) and a soft warning about a future-dated tip shown only in interactive mode; neither protects the flagged path, where refusal arrives only as a downstream error message.

Description

The balance chain needs a row to start from. An entry dated before the first stored row is refused with the explanation that balances cannot be carried forward — sound, but it arrives as a rejection at save time rather than guidance at capture time on the flagged path. The interactive flow does warn (when the ledger's last row is dated in the future, the question says so), yet a flagged capture with an early date learns nothing until the save fails.

Any change that relaxes the predecessor requirement, or that lets future-dated rows multiply unconfirmed in the ledger, would compound this: every later real capture would then have to date after the future row to keep the chain intact.
