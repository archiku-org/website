Remove recorded entry

Process Name

Remove a recorded entry

Title

Remove recorded entry

Summary

A recorded entry that must not be in the books — a duplicate, a test row, a payment that never happened — is removed for real after a typed yes: the owner's one request is answered by whichever register the entry lives in, as a journaled deletion, a register withdrawal, a group dissolution, or a one-date suppression.

Description

The owner states that a line in the books must go — by naming it, or by choosing from the ten most recent landed rows when nothing is named; an empty choice cancels before anything else happens. The books work out what kind of thing was named: a row already committed to the ledger, a future expectation, a statement group, or one projected date of a recurring rule. Every kind is shown in full before the owner is asked to consent, and consent must be typed — pressing Enter alone never removes anything, and a refusal leaves the books exactly as they were.

For committed money the removal is itself a recorded act: a new history event is written carrying the removed row's complete picture — its date, wording, category, account movements and links — and before that event is applied the books check it against the row as it actually stood; a mismatch stops loudly rather than let the history claim a deletion that never matched. The row is struck and every later row's running balances are re-earned from that point on, so no saldo keeps a hole. Removing a transfer is wider than it looks: the paired savings-side row leaves the ledger with it, and the owner is warned afterwards to re-check the account listing.

For what has not yet happened the answer is gentler: a future expectation is withdrawn from the register of plans without a history event; a statement group is dissolved and its members survive untouched; a projected rule date joins the rule's exceptions so that one period is skipped while the rule keeps running for the remaining ones — asking twice reports that the instance was already suppressed. An id that matches nothing at all is refused with the unknown-id answer; nothing is written, nothing changed. No path offers an undo: what must come back is re-captured by hand; only the history itself remembers what was removed, and for committed rows only — plans that are withdrawn leave no trace beyond the register file.

Trigger

An entry must not be in the ledger at all — duplicate capture, test row, or a payment that did not happen. Surface: the financials delete command.

Note

Refinement of the detection draft — the deep trace established the resolver precedence (ledger row, expectation, group, projected instance), the pre-image verification behind delete events, the idempotent suppression write, and the transfer's two-sided removal with its post-hoc warning.

process "Owner"
  start "A recorded entry must not be in the books"
  user "Invoke the delete command by id or pick from the recent rows"
  receive "Consider the shown entry and the confirmation request"
  user "Type the confirmation"
  receive "See the removal outcome"
  end "The books reflect the removal or the cancellation"

process "financials delete command"
  start "Delete request arrives"
  task "Resolve the entry's kind across the registers"
  exclusive "Entry found?"
    if "No" then
      task "Refuse the unknown id and change nothing"
      end "Unknown id refused" message
    else "Yes"
  task "Show the entry and ask for the typed yes"
  receive "Receive the typed answer"
  exclusive "Typed yes?"
    if "No" then
      task "Leave the books untouched"
      end "Removal cancelled" message
    else "Yes"
  exclusive "Which kind of entry?"
    if "Committed ledger row" then
      task "Append the delete event carrying the row's full picture"
      task "Re-earn the later rows' saldos"
      task "Warn about the touched savings chain when a transfer was removed"
    if "Future expectation" then
      task "Withdraw the row from the register of expectations"
    if "Statement group" then
      task "Dissolve the group and leave the members untouched"
    else "Projected rule date"
      task "Add the date to the rule's exceptions"
  end "Removal handled" message
