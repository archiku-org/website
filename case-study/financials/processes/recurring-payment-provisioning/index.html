Recurring payment provisioning

Process Name

Recurring payment provisioning

Title

Recurring payment provisioning

Summary

Repeating payments (rent, salary, subscriptions) are detected as candidates from the committed history, reviewed by the bookkeeper, and approved as recurring rules that drive the ledger's forecast.

Description

A recurring payment's life runs from noticing to trusting. The bookkeeper, seeing that the same bill arrives month after month, asks the tool to scan the committed history for patterns — same description and category, regular spacing, occurring often enough. The answer is a review table of candidate rules and the tool's own promise on its foot: nothing has been created. Each proposal carries the detected pattern — description, category, a representative amount (with the honest low-to-high range when amounts vary), the cadence and spacing, and when the pattern started. Taking a proposal opens the field-by-field editor seeded with those values: the bookkeeper keeps or overwrites each, gets the same validation every recording meets, and only then does the rule enter the recurrences store. From that moment the rule works for the forecast invisibly: each due date projects an instance into the view until real money matching the category, amount and timing covers it, or the bookkeeper pauses, re-edits or retires the pattern (pause is reversible; removal takes a typed confirmation and erases only the rule, never the history that made it). The forecast layer never touches the books — rules are an overlay on the journal's story of committed money; only a later explicit confirmation of a due instance creates journal entries. Detection, approval and rule management live in the recurrence commands; the engine's own rules — detection stores nothing, approval saves nothing until the loop completes — make every act here either a review or an explicit, validated write.

Trigger

The bookkeeper turns a repeating payment pattern in the history into a forecastable recurring rule (surface: the financials recurrence detect | add commands)

Note

BPMN XML

process "Household bookkeeper"
  start "A repeating pattern is worth a standing rule"
  user "Run the detection review"
  exclusive "Does the table hold a proposal?"
    if "No" then goto "The provisioning cycle closes"
    else "Yes"
  user "Review the proposals row by row"
  user "Take a proposal into the seeded editor"
  exclusive "Does the rule clear validation?"
    if "No or quit" then goto "The provisioning cycle closes"
    else "Yes"
  send "Approve the rule into the store"
  receive "Read the confirmation and upcoming dates"
  exclusive "Does the bill later stop or change?"
    if "Yes" then user "Pause, resume, remove or re-edit the rule"
    else "No"
    end "The provisioning cycle closes"

process "recurrence engine"
  start "Detection requested"
  service "Scan the committed history for candidate rules"
  rule "Hold the spacing and occurrence bar"
  service "Compose the proposal rows"
  end "Proposal table ready" message
  receive "Approved rule received"
  service "Record the approved rule in the recurrences store"
  service "Report the rule and its next due dates"
  end "Rule provisioning complete" message
  goto "Approved rule received"

message flows
  from "Household bookkeeper"."Run the detection review" to "recurrence engine"."Detection requested" label "Detection request"
  from "recurrence engine"."Proposal table ready" to "Household bookkeeper"."Review the proposals row by row" label "Proposal table"
  from "Household bookkeeper"."Approve the rule into the store" to "recurrence engine"."Approved rule received" label "Approved rule"
  from "recurrence engine"."Rule provisioning complete" to "Household bookkeeper"."Read the confirmation and upcoming dates" label "Store confirmation and next due dates"
