Entry revision

Process Name

Entry revision

Title

Entry revision

Summary

The bookkeeper corrects a recorded transaction or a planned entry — a new date, amount, description or category — and every journaled correction re-derives the books afterwards instead of silently rewriting history: a recorded entry's correction rests as a full restatement of its data, an edit into the future turns the recorded entry into a plan, and a landed plan's edit books the plan as it now stands.

Description

A recorded figure turns out to be wrong — a typo'd amount, a moved date, a miscategorized spend — or a planned entry needs its numbers adjusted before the day it lands. The household bookkeeper picks the entry by its id from the list view, or runs the edit bare and picks from the last ten rows (only entries already dated up to today are offered). The editor shows the row as it stands and walks one pass over date, description, category and amount, each field kept by pressing Enter and replaced only by re-typing it. Where the correction lands depends on what the entry is and where its date now falls. A recorded entry corrected to today or earlier is journaled as one event that restates all four of its data values — the books are then re-derived so every later day's running balance stays truthful, and the confirmation line shows the corrected entry with the new checking and savings balances. A recorded entry whose corrected date falls in the future leaves the committed books: it is removed and re-created as a plan at the new date — a sequencing that deliberately removes first, so a failed re-creation leaves the entry in neither store and names the recovery path; for transfers the bookkeeper is warned to check the savings side afterwards. A plan edited toward today or the past is intent to confirm — the plan books into the ledger with its values unchanged or newly edited, and is struck from the register only after the booking succeeded; on a plan that already landed, accepting every field with only Enters is confirmation by itself. A plan that stays in the future is simply rewritten where it sits in the register. Two guardrails shape every session: a wiped description abandons the whole edit without storing anything, and a row carrying no amount at all refuses to be edited. Entries that are actually groups or recurring-plan instances are handed to their own dedicated editors, and an id that names nothing is refused. The correction is provable rather than silent — every journaled route appends an event carrying the full state, so the journal can later show which correction happened and when.

Trigger

A recorded or planned entry contains wrong data and must be corrected (surface: the financials edit command)

BPMN XML

process "household bookkeeper"
  start "A recorded figure turns out wrong or a plan needs adjusting"
  user "Name the entry or pick from the last ten rows"
  receive "Read the outcome of the correction"
  end "The session closes with the books truthful"

process "interactive entry editor"
  start "An edit request arrives"
  exclusive "What does the id name?"
    if "A committed ledger row" then
      user "Show the row and walk the pre-filled form"
      exclusive "Did the form change anything?"
        if "Nothing changed" then
          end "Report nothing changed"
        else "A change was recorded"
      exclusive "Does the edited date land after today?"
        if "Yes" then
          send "Ask the ledger to remove the row"
          receive "Take back the removal"
          send "Ask the register to store the planned replacement"
          receive "Take back the register's answer"
          exclusive "Did the planned entry save?"
            if "No" then
              end "Name the recovery"
            else "Yes"
          end "Report the move to a plan"
        else "No"
      send "Ask the ledger to journal the full replacement"
      receive "Take back the applied row and balances"
      end "Report the corrected row and balances"
    if "A planned entry" then
      user "Show the plan and walk the pre-filled form"
      exclusive "Does the edited date land today or earlier?"
        if "Yes" then
          send "Ask the ledger to book the plan as it stands"
          receive "Take back the booked entry and balances"
          send "Ask the register to strike the plan"
          receive "Take back the register's strike"
          end "Report the confirmed plan"
        else "No — still future"
          send "Ask the register to rewrite the plan in place"
          receive "Take back the register's rewrite"
          end "Report the rewritten plan"
    if "A group or rule instance" then
      end "The owner editor continues"
    else "Nothing resolvable"
      end "Report unknown id"

process "journaled ledger engine"
  start "A journaled change is asked for"
  exclusive "Which change?"
    if "A recorded row is replaced" then
      service "Remove the row and rebalance the later days"
      service "Insert the replacement at its new date and rebalance"
    if "A moved row is removed" then
      service "Remove the row and reverse its balance effects"
    else "A plan is booked"
      service "Book the plan and tie it to the retired plan"
  send "Report the applied row and balances"
  end "Records stand corrected"

process "expected register store"
  start "A register change is asked for"
  exclusive "Which change?"
    if "A moved row becomes a plan" then
      service "File the new plan in the register"
    if "A confirmed plan must leave the register" then
      service "Strike the confirmed plan from the register"
    else "A still-future plan is rewritten"
      service "Rewrite the plan's stored details"
  send "Report the register's answer"
  end "Register answered"
