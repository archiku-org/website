Open-entry confirmation

Process Name

Open-entry confirmation

Title

Open-entry confirmation

Summary

A landed bill or payment that was only planned (expected entry or recurring-rule instance) is confirmed in one step as actually paid; the plan registers are cleaned up and the payment enters the actual ledger as a journaled transaction.

Description

A payment the household had only planned — a one-off expected entry or an instance of a recurring rule such as rent or insurance — has now landed at the bank. The bookkeeper confirms it in one step without being asked anything: the planned figure commits as-is, because adjusting values is the edit surface's job done beforehand. For an expected entry the confirmation books the planned values through the same booking doors as any manual recording, carrying the plan's identifier on the committed row so the books prove which plan this payment settled; only then is the plan struck from the expected register, never before a successful booking (a refused confirm — future date or missing amount — removes nothing). For a rule instance the rule's own values commit with no questions and no per-instance record: a booking that still covers the rule's period supersedes the instance silently, while a drifted commit (amount or date moved beyond tolerance) additionally records the occurrence as an exception on the rule so the stale projection leaves the open view. A group confirmation walks the landed members in date order — each commits through its own path, each confirmed plan member is re-pointed to its new committed identifier inside the group's membership, and future, amountless or unresolvable members are skipped with notes while the group itself survives. With no id given, the confirm picker shows the open backlog — everything landed but unconfirmed on or before today — and a single prompt asks which id to confirm; empty input cancels without changing anything. Already-settled identifiers are recognized and answered with a nothing-to-do note, so repeated or over-eager confirming can never double-book. Who perceives it: the household bookkeeper; what changes: planned money becomes recorded money, plan registers shrink, the journal proves the retirement, and the open backlog drains. Traced end to end this engagement: the dispatch (confirm.py confirm_transaction:232), the zero-prompt plan commit (confirm.py _confirm_expected:64, _commit_expected:38), the instance commit core (recurrence_cli.py commit_instance:596) and the group walk (confirm.py _confirm_group:124).

Trigger

A planned payment (expected entry or recurring-rule instance) has actually landed and must be committed as paid (surface: the financials confirm command)

Note

Deep-analysis refinement (carter detail task). Script composed and validated (bpmn_tools:validate: valid) on the second composition — first attempt failed once on a duplicate node name, fixed at source. No stored validation failure.

BPMN XML

process "Household bookkeeper"
  start "A planned payment has landed at the bank"
  user "Decide to confirm the landed entry"
  exclusive "Is the confirmation an id, a bare confirm or a group?"
    if "An id of a landed plan" then
      service "Book the planned values as a confirming payment"
      exclusive "Is the plan dated after today or missing its amount?"
        if "Yes" then
          task "Refuse with a note that nothing was confirmed"
          end "Plan untouched"
        else "No then book and strike the plan"
      task "Strike the plan from the expected register"
      task "Confirm the new balance on the receipt"
      end "Plan confirmed as booked money"
    if "An id of a due rule instance" then
      exclusive "Is the instance dated in the future?"
        if "Yes" then
          user "Adjust the pre-filled date and amount for the early-landed instance"
          exclusive "Is the confirmed date still ahead of today?"
            if "Yes" then
              task "Refuse — a real payment never lies in the future"
              end "Instance untouched"
            else "No then commit"
          service "Book the adjusted values and record an exception if the values drifted"
          end "Instance confirmed as booked money"
        else "No land today then commit as-is"
      service "Book the rule's own values with no questions"
      end "Instance committed with the rule's values"
    if "A group id" then
      parallel
        do service "Book each landed member plan with its own confirming payment"
        do service "Book each landed rule-instance member from its rule"
      task "Re-point each confirmed member to its booking in the group"
      task "Report the skipped members"
      end "Group confirmed as far as it landed"
    else "Bare confirm with no id"
  user "Read the open backlog table and pick an entry"
  goto "Decide to confirm the landed entry"
