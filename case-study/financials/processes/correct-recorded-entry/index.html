Correct recorded entry

Process Name

Correct a recorded entry

Title

Correct recorded entry

Summary

A recorded entry turns out wrong or incomplete — the owner names it to the edit command (id or pick-from-recent), the program resolves the entry's kind and opens pre-filled prompts, and the correction lands by kind: a journaled update for committed rows, a register update or confirm for expectations, a relabel for statement groups, and the rule-versus-occurrence choice for projected rule occurrences. Nothing changes without review; a declining owner cancels with nothing stored.

Description

An error surfaces after recording: a wrong amount, a mistyped description, a mis-categorized expense, a wrong date. The owner runs the financials edit command, naming the entry by its id from the ledger list — or nothing at all, in which case the program shows the ten most recent committed rows and the owner picks one (edit.py:123-138, cli.py:113-123).

The program decides what kind of thing was named, in a fixed order: a committed ledger row, then an open expectation in the register, then a statement-group rollup, then a projected occurrence of a recurring rule (edit.py:274-303, the four-kind resolver concept). Only when all four decline does the owner hear "unknown id" — and a decline inside the occurrence editor is always a cancel, never that message.

Each kind opens its own editor, all prompts pre-filled with the entry's current values, Enter keeping and 'q' or an empty description cancelling (edit.py:66-113). For a committed row, the corrected fields become one journaled update event and the ledger view is re-derived from the whole corrected history — history is never rewritten (commands.py:128-149, journal.py:287-307). When the corrected date moves the row ahead of today, the entry instead leaves the ledger by a journaled removal and re-enters the register as an expectation; if the recreate fails, a recovery message names the expect command (edit.py:208-236). For an expectation that has already landed — one whose date is today or earlier, or that the owner's edit moves there — the edit becomes a confirmation: one event lands the actual and retires the expectation (edit.py:147-162, 165-205); a still-open expectation is simply updated in the register. For a statement group, only the group's own fields are editable — name, rollup date, category, note — never the member rows (groups.py:338-370). For a projected rule occurrence, the owner chooses: adjust the whole rule for every occurrence to come, or handle just this one — confirming a landed occurrence as a real transaction with rule-prefilled values, or recording a future occurrence's deviation as an exception that exempts it from the projection while the rule keeps running (recurrence_cli.py:746-813, 596-646).

After every committed-path change the journal is replay-checked against the recomputed ledger and the checkpoint persists, so the current view always reflects the corrected history and a hand-rewritten book fails its own verification on boot (commands.py:72-85, journal.py:449-532). The owner sees the outcome with the updated account balances; the balances themselves are never editable — a wrong saldo is repaired by correcting the entry, never by setting the balance (edit.py:66-113).

One traced boundary question stays open with the business: an expectation reserved with a deliberately zero amount flows through the as-is confirm into a zero-amount committed row — the books' no-zero law does not reach that path, and whether that is gap or grace is not decodable from the code (edit.py:147-149, commands.py:98-125; the rule-interference and hotspot facts record it).

Trigger

A recorded entry turns out to be wrong — the owner needs to fix history or an open entry. Surface: the financials edit command.

Note

BPMN XML

process "Owner"
  start "A recorded entry turns out wrong"
  user "Name the entry to correct or pick it from the ten most recent rows"
  receive "See the outcome and the updated balances"
  end "Entry corrected"

process "Financials program"
  start "Edit request arrives"
  task "Resolve the named id against the ledger, expectations, groups and rule occurrences"
  exclusive "What kind of entry was named?"
    if "Committed row" then
      user "Walk the committed row's pre-filled prompts with the owner"
      exclusive "Does the corrected date move the row ahead of today?"
        if "Ahead of today" then
          task "Remove the committed row from the ledger, journaled"
          task "Recreate the entry as an expectation at the new date"
          goto "Report the outcome and the updated balances"
        else "Today or earlier"
          task "Record the correction as a journaled update, replay-checked"
          goto "Report the outcome and the updated balances"
    if "Expectation" then
      user "Walk the expectation's pre-filled prompts with the owner"
      exclusive "Has the expectation landed on or before today?"
        if "Landed today or earlier" then
          task "Confirm the entry as a real transaction, retiring the expectation, replay-checked"
          goto "Report the outcome and the updated balances"
        else "Still open"
          task "Update the expectation in the register"
          goto "Report the outcome and the updated balances"
    if "Statement group" then
      user "Walk the group's pre-filled relabel prompts with the owner"
      task "Update the group's name, rollup date, category and note"
      goto "Report the outcome and the updated balances"
    if "Projected occurrence" then
      user "Ask the owner: adjust the whole rule or handle only this occurrence"
      exclusive "What did the owner choose?"
        if "Adjust the rule" then
          task "Open the recurring rule's editor"
          goto "Report the outcome and the updated balances"
        else "This occurrence only"
          exclusive "Has the occurrence landed?"
            if "Landed" then
              task "Confirm the occurrence as a real transaction, replay-checked"
              goto "Report the outcome and the updated balances"
            else "Still ahead"
              task "Record the deviation as an expectation and exempt this occurrence"
              goto "Report the outcome and the updated balances"
    else "Unknown id"
      task "Tell the owner the id was not recognised"
      goto "Report the outcome and the updated balances"
  user "Report the outcome and the updated balances"
  end "Correction handled"

  from "Financials program"."Report the outcome and the updated balances" to "Owner"."See the outcome and the updated balances" label "Correction result"
