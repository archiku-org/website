Process Name

Manage recurring rules

Title

Manage recurring rules

Summary

Standing financial commitments live as recurring rules — defined once with cadence and amounts, kept current through pause, resume, edit or removal; each period their occurrences stand in the open view until a real movement lands, and the books' own history can propose new rules for the owner to adopt.

Description

Money that repeats — rent, insurance premiums, salary, subscriptions — is stated once as a recurring rule and then feeds the open view every period, so the owner never enters the same bill by hand.

Stating the commitment: the owner gives the description, category, amount, cadence and anchor details; whatever is missing is asked, never assumed, and any question can be abandoned — an abandoned statement stores nothing. The rule must pass the house checks (approved category, non-zero amount, valid dates, one of the four cadences) before it is saved, and an annual or weekly rule is asked for its month or weekday anchor exactly like its prefilled sibling paths. A day-29-to-31 rule is warned honestly that short months skip their occurrence.

Keeping it current: the listing shows every rule and its next few occurrences; a suspended commitment is paused and returns with resume; an amount or schedule that life changed is edited through the keep-or-replace field loop; a commitment that is gone for good is removed only after a typed confirmation.

Living with the forecast: each period the rule's occurrences stand in the open view with resolvable identities, filtered by four honesty gates — the rule must be active, inside its own lifetime, the date must not be one of its recorded exceptions, and no committed movement may already cover it. When the bill actually lands, confirming the occurrence commits it straight from the rule's values, zero-prompt; only an early-landed bill asks anything, and even then the rule's values are the prefilled starting points and the date may only move down to today. A real row the owner booked independently covers the occurrence automatically, so nothing double-books; a commit that drifted away from the schedule records the occurrence as an exception so it leaves the open view. An occurrence that will not happen is suppressed — its date joins the rule's exceptions and the rule keeps running for every other period — and a single occurrence can otherwise be replaced by a one-off plan or adjusted by editing the rule itself, the two-option choice named by the instance editor.

Learning from history: the detector reads committed movements for repeated patterns — near-constant amounts, or timely series with varying amounts proposed by their median and observed range — and shows candidates in a review table, creating nothing; adoption walks the prefilled field loop and saves only through the same house checks, and groups already covered by a rule are never re-proposed.

Trigger

A standing financial commitment needs maintaining, or a recurring bill landed and must be committed. Surface: the financials recurrence command and the rule-instance branches of confirm, edit and delete.

Note

Refined by the deep detail pass — script composed and validated, steps mirrored to the traced code paths (definition, maintenance, projection filters, confirm and drift branch, edit and suppression, detection and adoption).

BPMN XML

process "Owner"
  start "A standing commitment needs attention"
  exclusive "What does the commitment need?"
    if "Define or adjust it as a rule" then
      send "State the rule's details and answer the questions"
      receive "See the rule saved or the reason it was not"
    if "A recurring bill landed" then
      send "Confirm the occurrence as booked"
      receive "See the commitment marked as landed"
    if "Only review it" then
      send "Ask for the rules and their next occurrences"
      receive "See the rules and their forecasts"
  exclusive "More standing commitments to tend?"
    if "Yes" then goto "What does the commitment need?"
    else "No"
  end "The rule set reflects the commitments"

process "Financials program"
  start "A commitment request arrives"
  script "Serve the request and run the house checks on what was stated"
  exclusive "Did the request pass the checks?"
    if "No" then
      task "Tell the reason and store nothing"
      end "Nothing stored"
    else "Yes"
  script "Do the accepted work — save the checked rule, commit a landed occurrence or project the forecast window"
  end "Request served"
