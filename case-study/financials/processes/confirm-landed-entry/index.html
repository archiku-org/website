Confirm landed entry

Process Name

Confirm a landed entry

Title

Confirm landed entry

Summary

A landed but uncommitted entry — a matured expected row, a billing-rule occurrence, or a whole statement group — is confirmed in one step, committing it to the journal as an actual with its values as-is.

Description

The recurring moment of the ledger: money movement that was only forecast has now really happened, and the owner blesses it. They run the confirm command with the entry's id — or bare, picking from the OPEN section, the landed-but-unconfirmed backlog.

The confirm engine resolves what kind of open entry was offered. An already-committed id answers "already actual — nothing to do"; an unknown id reports as unknown. An expected row commits as-is through one journaled event that retires the expected identifier and lands the actual together, after which the register drops the settled row — but future-dated (refused, edit first) or amount-less rows never reach this point. A landed rule occurrence commits with the billing rule's own values, zero prompts; a still-future occurrence opens the pre-filled interactive walk (date may shift down to today, never ahead). A group id commits every landed member in date order — expectations via the same journaled swap, rule members only after a coverage check so nothing double-books — and re-points each member's id to its new committed identity so the group survives.

The commits themselves land in the ledger engine: stamped, content-identified journal events; the ledger replays to running balances and the checkpoint converges. The verdict returns to the owner: the committed id, the retired expectation, the new balances — and for transfer bookings a reminder that the savings chain moved too.

Trigger

Forecast money movement has landed in reality — a scheduled payment has matured or a statement has arrived, and the owner commits it. Surface: the financials confirm command (by id or picked from the OPEN section).

process "Owner"
  start "A forecasted movement has landed"
  task "Pick the landed entry to confirm"
  send "Hand the entry to the books for confirmation"
  receive "Receive the verdict with the balances"
  exclusive "Did the books take the movement?"
    if "Committed" then
      end "Entry stands as committed history"
    else "Not committed"
      user "Adjust the entry with the edit flow"
      goto "Pick the landed entry to confirm"

process "Confirm engine"
  start "Confirm request arrives"
  script "Work out which kind of open entry was offered"
  exclusive "Which shape is the open entry?"
    if "Already committed or unknown id" then
      send "Answer nothing to do or unknown id"
      end "No booking made"
    if "An expected entry" then
      exclusive "Landed and carrying an amount?"
        if "Yes" then
          service "Land the movement and retire the expectation in one recorded event"
          service "Drop the settled expectation from the register"
        else "No"
          send "Report the refusal and point to the edit flow"
          goto "No booking made"
    if "A whole statement group" then
      script "Walk the landed members in date order, committing each"
      service "Carry each member's new identity into the group"
    if "A landed rule occurrence" then
      service "Commit the occurrence with the rule's own values"
    if "A rule occurrence still in the future" then
      user "Walk the owner through the pre-filled values"
      service "Commit the occurrence with the confirmed values"
  receive "Receive the recorded result"
  end "Verdict with balances" message

process "Ledger engine"
  start "Commit request arrives"
  service "Record the confirmed movement"
  service "Settle the account balances"
  send "Return the verdict with the balances"
  end "Commit settled"
