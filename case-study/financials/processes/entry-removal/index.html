    Entry removal

    Process Name

    Entry removal

    Title

    Entry removal

    Summary

    When an entry turns out not to belong in the books at all, the bookkeeper removes it after explicit confirmation — actual transactions are journaled with their full pre-image so history stays provable, planned entries and rule occurrences are struck from their own planning stores.

    Description

    A double recording, a card payment logged twice as transactions, a planned entry no longer expected — the bookkeeper opens the delete command and names the row, or lets it show the last ten past rows and picks from that menu. The typed id is resolved in exactly one place: the committed books first (by their content-derived ids), then the planned-entry register, then the grouped-row bundles, then the projected occurrences of recurring rules. Nothing is removed without a typed affirmative — bare Enter, an unknown word and an interruption all leave every store untouched. A committed transaction's removal is itself a recorded event: the removal joins the journal carrying the removed entry's complete content as it stood — date, description, category, its money movements across accounts and its links to other rows — read from the live books before anything changes. At every ledger read-back that stored snapshot is compared with what actually happened in the books, and a mismatch stops the books from opening at all rather than letting the journal silently claim a removal it did not make. The running balances of every later row are re-propagated so no drift remains, and removing a transfer earns an extra warning because the savings chain moved too. The planning stores have no such history: a planned entry is simply struck from the register, a projected rule occurrence is suppressed by adding its date to the rule's exceptions so the rule keeps running for the other periods, and a grouped bundle dissolves without touching its member rows. There is no undo — re-creating a wrongly removed entry means recording it anew; the journal is the audit trail of what was removed. A second door exists for planned entries on the expect surface that strikes without asking — a known deliberation point.

    Trigger

    Surface: the financials delete command — a recorded transaction or planned entry must be removed from the books.

    Note

    Refinement of the detection draft: the four-way resolver order, the confirmation law, the striking/suppression/dissolve paths and the engine-side pre-image verification were all traced this engagement. The script validated through the bpmn_tools gate (3 validate calls, 2 repairs — else-if chaining and a missing pool start).

    BPMN XML

    process "household bookkeeper"
  start "An entry turns out not to belong in the books"
  user "Open the delete command with the row's id, or bare to pick from the last ten past rows"
  exclusive "Which store owns the id?"
    if "A committed transaction" then
      user "Show the row and type an affirmative to confirm the removal"
      send "Removal request with the row's id"
      receive "Removal receipt — the transaction is gone, the journal holds its full pre-image"
      user "Check the ledger listing when the removed row was a transfer"
    if "A planned entry" then
      user "Show the planned entry and type an affirmative to confirm the striking"
      send "Striking request with the plan's id"
      receive "Striking receipt — the plan leaves the register, no history written"
    if "A group id" then
      user "Show the group and confirm the dissolve"
      send "Dissolve request with the group's id"
      receive "Dissolve receipt — the bundle is gone, the member rows keep existing"
    if "A rule-instance id" then
      user "Show the projected occurrence and confirm the suppression"
      send "Suppression request with the occurrence's id"
      receive "Suppression receipt — the occurrence leaves the forecast, the rule keeps running"
    else "Unknown id" then
      user "Hear that the id matches nothing and leave the books untouched"
  end "The books no longer carry the entry; the journal proves what was removed"

process "interactive deletion dispatcher"
  start "A removal request arrives"
  task "Resolve the typed id against the committed books"
  exclusive "Which store owns the id?"
    if "A committed transaction" then
      task "Show the row and require the typed affirmative"
      service "Snapshot the entry's full content from the live books"
      service "Journal the removal with the pre-image snapshot and re-propagate the balances"
      send "Removal receipt — with the transfer warning when the category was a transfer"
      end "Transaction removed — the journal proves the removal"
    if "A planned entry" then
      task "Show the planned entry and require the typed affirmative"
      task "Strike the planned entry from its register"
      send "Striking receipt"
      end "Planned entry struck — nothing journaled"
    if "A group id" then
      task "Dissolve only the grouping, member rows untouched"
      send "Dissolve receipt"
      end "Group dissolved — member rows keep existing"
    if "A rule-instance id" then
      send "Suppression request with the occurrence's id"
      end "Occurrence handed to the rule's engine"
    else "Unknown id" then
      task "Report that the id matches nothing"
      end "Nothing removed"

process "recurrence engine"
  start "A suppression request arrives for a projected occurrence"
  task "Match the occurrence to its rule and check the rule's exceptions"
  exclusive "Already suppressed?"
    if "Yes" then
      user "Report that nothing more will change"
      end "Nothing more changes"
    else "No" then
      task "Require the typed affirmative and add the occurrence date to the rule's exceptions"
      send "Suppression receipt"
      end "Occurrence suppressed — the rule keeps running for the other periods"

process "journaled ledger engine"
  start "A removal carrying the victim's pre-image arrives"
  task "Read the live entry for the target id and refuse when it is not there"
  task "Append the content-hashed removal record and fold it onto the books"
  exclusive "Does the stored pre-image match the live entry at replay?"
    if "No" then
      task "Refuse loudly — the books will not open until the journal is repaired"
      end "The removal is refused — the journal waits for repair"
    else "Yes" then
      task "Splice the entry out and re-propagate the running balances into every later row"
      send "Removal applied — receipt back to the dispatcher"
      end "The removal is durable, replayable and balance-correct"
