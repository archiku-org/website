    Ledger cleanup-fx application

    Process Name

    Ledger cleanup-fx application

    Title

    Ledger cleanup-fx application

    Summary

    Reviewed change-set files containing corrected field values are applied to the journaled ledger oldest-first, each application recorded in an append-only application journal, with the fix files renamed applied when consumed.

    Description

    Historical mistakes that predate the tool — or bulk corrections reviewed offline — arrive as small change-set files: each fix in a file names one ledger row and states what should change about it (a corrected field with an optional old value as a drift guard, or a whole-row action: striking the row, or clearing a parked plan). The household bookkeeper points the fix command at one reviewed file, or lets it sweep every pending file in the data directory, oldest first. For each fix the tool re-reads the live ledger and checks the guards: the row must be known and unambiguous, any stated old value must still match, and a removal's captured content must equal the live row. A fix that passes becomes exactly one recorded change to the books — the appended record carries the corrected row in full, the ledger rebooks the row (remove and re-insert on the same identity) and re-derives every later running balance, then the record's file snapshot converges. A refused fix stops the run at that fix with a message naming row, field and the two disagreeing values: everything earlier in the file stays applied, nothing afterward applies, and the file is not renamed. When all of a file's fixes land, the sweep renames the file with an applied suffix so it never runs twice, and the next file begins. Removals aimed at parked plans clear the register directly — plans are not part of the books, so no recorded change exists for them. The bookkeeper reads the run's table (each fix's outcome beside its stated reason) and repairs any refused file before rerunning; the change journal itself is the durable account of what actually reached the books.

    Trigger

    Reviewed correction change-sets for historical data are pending and must reach the ledger (surface: the financials fix command)

    Note

    Deep-trace refinement: every step verified in the code this engagement (cli.py fix dispatch, fixes.py loaders/guards/sweep, commands.py write step, journal.py rebook). Script validated by bpmn_tools. Detection's trigger confirmed unchanged.

    BPMN XML

    process "household bookkeeper"
  start "Reviewed cleanup change-sets are ready to apply"
  user "Hand one change-set file or the whole pending set to the tool"
  receive "Read the application outcome"
  exclusive "Every change-set applied cleanly?"
    if "No - a fix was refused" then
      user "Repair the refused fixes in the change-set"
      goto "Hand one change-set file or the whole pending set to the tool"
    else "Yes"
  end "Books cleaned up"

process "cleanup fix engine"
  start "Apply request arrives"
  service "Load the reviewed fixes from the change-set"
  task "Resolve one fix against the ledger and check its guards"
  exclusive "Fix is clear?"
    if "No" then
      end "Run aborted at the refused fix"
    else "Yes"
      service "Land the correction as one recorded ledger change"
  exclusive "More fixes in the change-set?"
    if "Yes" then goto "Resolve one fix against the ledger and check its guards"
    else "No"
  exclusive "Pending sweep mode?"
    if "Yes" then
      service "Mark the applied change-set with the applied marker"
    else "No"
  end "Change-set fully handled"

process "journaled ledger engine"
  start "One fix's recorded change is ready"
  service "Mint the record's content identity and append it to the change journal"
  service "Rebook the ledger and persist the converged snapshot"
  end "The change is recorded"
