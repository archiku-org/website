Apply cleanup fixes

Process Name

Apply cleanup fixes

Title

Apply cleanup fixes

Summary

Reviewed correction batches — JSON or TOML files next to the ledger data — are applied oldest-first through the same journaled write core as interactive changes: each field correction lands as one update event carrying the row's final state, each committed-row removal as a removal event, and plan acts edit the register of plans directly; a consumed batch file is marked applied so it never applies twice.

Description

A reviewed batch of corrections sits in a file the reviewer prepared outside the program — JSON or TOML, one list under the name "fixes". The bookkeeper hands a batch to the program: one named file, or every pending corrections file gathered oldest first. The batch is split by shape: an entry carrying a field corrects one field of one recorded row; an entry carrying an act removes a row or adds a planned one.

Every field correction resolves its row first — by full id or an unambiguous prefix, refusing ambiguity — then checks the row's current value against the correction's stated old value when one is stated, and only then journals one update event carrying the row's whole final picture: date, wording, category, account movements. A transfer row keeps both legs opposite when its amount is corrected. Row acts split by residence: a removal naming a committed row journals a removal event with the row's full picture; a removal naming a planned entry withdraws it from the register of plans with no journal event (an id matching neither store refuses); an addition writes the new plan straight into the register.

Each change rides the program's single journaled write step, so history stays reconstructible line by line, and a guard refusal never writes its own entry — every journal line records a change that happened. But the batch is not atomic: a refused entry stops the run with earlier entries already applied, the file stays pending, and every later run re-applies the leading entries and refuses at the wedge again until a human fixes or removes the file. After a fully successful apply-all run the consumed file is renamed with the applied marker so the same batch can never apply twice; a single-file application does not mark, leaving that file in the pending scope (an asymmetry flagged for the business to judge). The batch surface answers in English while the interactive surfaces speak Dutch.

Trigger

Reviewed data corrections are ready as fix files and must reach the ledger. Surface: the financials fix command with a file or the apply-all form.

Note

Deep-traced 2026-10-23 — the batch path rides the journaled write core with per-entry guards; the applied marker exists only on the --all pass (flagged as a hotspot for the business).

BPMN XML

process "Bookkeeper"
  start "A reviewed batch of corrections is ready"
  user "Choose the batch to apply"
  send "Hand the batch to the program"
  receive "Hear the application outcome"
  exclusive "Did every entry land?"
    if "An entry was refused" then
      user "Correct the batch file by hand"
      goto "Choose the batch to apply"
    else "Applied"
  end "The books carry the reviewed corrections"

process "financials program"
  start "Batch application requested"
  exclusive "One named file or all pending?"
    if "All pending" then
      service "Gather the pending fix files oldest first"
    else "One named file"
      service "Load the named batch file"
  service "Split field corrections from row operations"
  exclusive "What does the entry act on?"
    if "A field of a recorded row" then
      service "Check the row and its stated old value"
      exclusive "The correction is safe to receive?"
        if "Yes" then
          service "Journal one update event with the row's final state"
        else "No - refuse loudly"
          end "The batch stops at the refused entry"
    else "A whole row"
      exclusive "Which row act?"
        if "Remove a recorded row" then
          service "Journal a removal event with the row's full picture"
        if "Withdraw a planned entry" then
          service "Drop the plan from the register"
        else "Add a planned entry"
          service "Write the new plan into the register"
  exclusive "More entries in the batch?"
    if "Yes" then
      goto "What does the entry act on?"
    else "No"
  service "Report the applied count"
  exclusive "Was this an all-pending run?"
    if "Yes and every entry landed" then
      service "Mark the consumed file applied"
    else "No"
      service "Leave the file as is"
  end "Batch application complete"
