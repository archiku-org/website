    Commit a recurring rule instance into the ledger

    Process Name

    Rule instance commitment

    Title

    Commit a recurring rule instance into the ledger

    Summary

    Brings a standing rule's projected occurrence into the books — as the rule promised it, as a reshaped one-off promise, or as a deliberately silenced date — while the rule keeps anticipating every other period.

    Description

    The forecast shows every active standing rule's upcoming occurrences, and the owner meets them through a booking door. When a recurring bill's day arrives, the owner can take the occurrence straight to the confirmation desk: it books the money exactly as the rule promised — no questions — unless the owner walked a still-future occurrence first, where every value is offered prefilled and the day may be shifted to when the money actually landed. After posting, the books either count the occurrence as handled — the movement matched the rule's mark: same category, essentially the same amount, near the planned day — or the booking had drifted, and the occurrence is kept off the forecast as an exception so nothing keeps nagging.

    The other doors reshape instead of booking. An occurrence that will differ from the standing rule — a different amount, a moved day — becomes a one-off promise of its own, admitted under the promise register's rules, and the original occurrence steps aside for that one month while the rule keeps running; a promise dated today or earlier is refused here, the one calendar the doors disagree on. An occurrence that should never book at all — a waived rent, a cancelled subscription — is suppressed after a typed yes: its date joins the rule's excepted days and the forecast goes quiet.

    Suppression is forecast-silencing only. The occurrence's derived address stays alive everywhere else, so the very occurrence the owner deleted can still be booked by its address later — nothing at either door recalls the earlier delete. The books record neither the suppression nor its reason; only the forecast silence remains.

    Trigger

    A recurring bill's occurrence lands in the account and the owner books it — surface: the confirm command on a rule instance id, edit on the instance, or delete as suppression

    process "Owner"
  start "The forecast shows the occurrence or its day arrives"
  user "Bring the occurrence's address to a booking door"
  exclusive "What does the owner want with this occurrence?"
    if "Book the money" then
      exclusive "Has the occurrence's day arrived?"
        if "Arrived" send "Hand the instance to the confirmation desk"
        if "Still ahead" then
          user "Walk the prefilled questions, the day asked first"
          exclusive "Does the typed day stay on or before today?"
            if "Ahead of today" goto "The occurrence is settled"
            if "Today or earlier" send "Hand the walked instance to the desk"
    if "Reshape this month into a promise" then
      user "Reshape the occurrence's fields, the day asked first"
      send "Hand the reshaped occurrence to the editor"
    if "Suppress this month" then
      user "Type the yes that approves the suppression"
      exclusive "Was the yes stated?"
        if "Yes" send "Hand the suppressed occurrence to the editor"
        if "No" goto "The occurrence is settled"
  user "See the posted result"
  end "The occurrence is settled"

process "Open-entry confirmation"
  start "The desk opens the instance"
  service "Post the movement and retire the promise"
  exclusive "Does the posting match the rule's mark?"
    if "On the mark" goto "The desk closes the occurrence"
    if "Drifted" service "Record this occurrence as the rule's exception"
  end "The desk closes the occurrence"

process "Recurrence planner"
  start "The editor opens the occurrence"
  exclusive "What was asked of the editor?"
    if "Suppress this occurrence" then
      service "Add the occurrence's date to the rule's exceptions"
    if "Reshape into a promise" then
      send "Offer the reshaped promise to the register"
      receive "Take the stored promise back"
      service "Except the occurrence replaced by the promise"
  end "The editor closes the occurrence"

process "Expected register"
  start "The register receives a reshaped promise"
  exclusive "Is the promise's day still strictly ahead of today?"
    if "Today or past" then
      end "The register rejects the promise"
    if "Still ahead" service "Store the promise under its own id"
  end "The register hands the promise to the books"
