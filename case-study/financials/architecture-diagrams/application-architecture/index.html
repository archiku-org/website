Name

Application architecture

Title

Application architecture

Summary

Whole-project architecture of the financials CLI: 25 components composed from the vault's component facts, grouped into 7 subsystem regions, with 47 connections traced to basset's internal import graph.

Description

This view composes the whole financials program: every node IS a vault component fact (25 of 25, none dropped, none invented), every region is a subsystem fact wrapping the components whose member-of links name it, and every connection is an internal import edge between the components' grounded-in file sets, taken verbatim from basset's dependency graph. The intake subsystem dominates the top of the board: the command-line door and interactive capture flow feed a single journaled write core; confirm, removal and correction all funnel into that same write machinery, the read side composes the ledger picture from history plus rule projections, statement grouping rides the group registry, and the recurring-commitments engine sits beneath, projecting occurrences into the view. Reading changes nothing and writes have exactly one door - that shape of the vault's own stories, which the edges restate.

What the view does NOT claim: connections are import dependencies, not runtime dataflow guarantees; the per-file edge resolution where one file grounds several components was composed by flow (see note); components whose imports ride a shared module (occurrence detection, statement rollup builder, edit-command fallback) show no connection even though they actively share territory; and the ungrouded support files (model, config, config_loader, parsing, tui/add) are not nodes because no component fact covers them - their absence is recorded, not filled.

Note

Shared-file resolution (file-level import edges where one file grounds several components, composed by flow, all line refs from basset's spine): commands.py grounds journaled-write-core, confirm-commit-core, journaled-delete-mutation and fixes-engine - confirm.py->commands.py resolves to confirm-commit-core (confirm.py:44,172,252); entry.py/edit.py->commands.py to the write core; delete.py->commands.py (delete.py:20,102) to the delete mutation (its prose quotes cmd_delete); the commands.py->journal.py edge (commands.py:19,186) is attributed to confirm-commit-core->journaled-write-core. journal.py grounds write-core and delete-mutation: imports resolve to write-core (mutation building) except delete.py->journal.py (delete.py:103), merged into the delete-mutation connection. edit.py grounds the edit resolver and its group-editor fallback: edit.py imports resolve to the resolver; the fallback carries no separate edges. groups.py grounds registry, member resolver, rollup builder (ledger-view-composition and the edit resolver also ground it): inbound imports resolve to group-registry, except ledger_view.py's (attributed to group-collapse, its membership reading) and edit.py's (group-editor handoff); groups.py's own imports of recurrence_cli/recurrences resolve from the member resolver (its re-expansion story) to rule-projection/rule-engine. ledger_view.py grounds composition and collapse: imports resolve to composition except ledger_view->groups. recurrence_cli.py grounds maintenance surface, definition flow, projection and detection: module imports attributed to definition flow (recurrence_cli.py:27 ask, 28+612 commands), maintenance (29+578 recurrences), projection (577,858,919 ledger_view; 788 expected); inbound cli.py->recurrence_cli.py (cli.py:372) resolves to the maintenance surface, while confirm/delete/edit/groups resolve to the projection (instance-id resolution per its prose). Deduplication: 5 component pairs received two file edges each (intake and edit and fixes and registry into the write core, delete into the delete mutation) and carry ONE connection each. Sources are bare repo paths: file facts carry loc but no spine line ranges, so none are guessed; each node also names its component fact id. Node types are backend except interactive-ledger-tui (frontend - its files import the textual/rich UI framework). Module-spine files grounding no component fact and therefore absent from the board: financials/init.py, config.py, config_loader.py, parsing.py, model.py, tui/add.py; scripts/ and tests/ are context spine branches outside the component census. Components with no connection despite being diagrammed: occurrence-detection, rollup-builder, edit-command-fallback (their shared module's import edges were attributed to siblings) - and visual-report draws only its cli routing edge, since its data path runs through model.py.
