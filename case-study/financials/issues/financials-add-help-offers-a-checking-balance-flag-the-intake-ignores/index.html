Financials add help offers a checking-balance flag the intake ignores

Title

Financials add help offers a checking-balance flag the intake ignores

Summary

The command's own help advertises "New checking balance (defaults to the continued balance)" for --checking, but the value is passed through and never used — a recording can never carry a hand-stated balance.

Description

A bookkeeper reading the command's help is told --checking sets the new checking balance. Following that instruction, they get silently ignored: the value travels from the command line into the intake call and stops there — no validation, no storage, no effect on the saved balances. There is no error and no warning; the balances are always the engine's derived ones. The help text states behavior (a balance override) the implementation does not have.

Rationale

Read the dispatcher's add wiring (cli.py main, add branch) and the intake call chain (add_transaction entry.py:181-287). The claim comes from the add parser's own --checking help text (cli.py:80-85). Tracing the flag's value: args.checking is forwarded to add_transaction(checking=...) at cli.py:283; a syntactic reference search of entry.py shows checking appears only in _prompt internals (108, 112, 167, 171, 172) and the unused parameter declaration (186) — the parameter's value is never read anywhere in the function body. So a caller-supplied balance cannot influence any stored balance, contradicting the advertised "new checking balance" behavior. Neither side is trivially the stale one — the derived-only balance design at the confirmation gate (entry.py:160-177) may be what stranded the flag; both the help and the code stand coherent internally, so the conflict is parked for review rather than attributed.
